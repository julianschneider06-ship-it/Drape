# Architecture (data pipeline, roadmap step 2 part 1)

## Data flow

```
shop (Shopify /products.json, later feeds)
  -> SourceAdapter.fetchPage()      src/ingest/adapters/*   (polite HTTP, backoff, cursor)
  -> adapter.normalize()            common schema: src/ingest/types.ts
  -> scripts/ingest.ts              batch job, 100 items per call, resumable
  -> edge function `pipeline`       database gateway (service key never leaves Supabase)
  -> SQL function ingest_batch()    one set-based upsert per batch
  -> tables: raw_items, products, offers, product_images
```

AI classification is not part of this step. `classification_queue` exists and is empty.

## Scale decisions

- **Sources are config.** A Shopify store is one line in `src/ingest/sources.ts`. New kinds (feeds, Zalando) implement the same `SourceAdapter` interface; nothing downstream changes. Zalando is an inactive stub: the site blocks bots (Akamai 403), so the plan is a partner/affiliate feed.
- **Raw first.** Every source item is stored untouched in `raw_items` (jsonb + content hash). Re-normalizing needs no re-crawl.
- **Idempotent by construction.** Unique keys: `raw_items(source_id, external_id)`, `offers(source_id, external_id)`, `products(canonical_key)`, `product_images(product_id, url)`. Running a batch twice changes nothing. `ingest_batch` is one set-based SQL call per 100 items, not row by row.
- **Canonical products, many offers.** `canonical_key = sha1(brand | name | colour | gender)` merges the same product from several shops into one `products` row with several `offers`. When the colour is unknown we do NOT merge (the key uses source + external id), because a wrong merge is worse than a missed one. Found the hard way: Outdoor Voices sells one colour per product and has no colour field.
- **Compact keys, targeted indexes.** `bigint identity` ids (no random-uuid index bloat). Indexes only on lookup paths: offers by product and by (source, last_seen), images by (product, position), products by (category, gender, id) and by brand, partial indexes for un-normalized raw rows and for pending queue rows. Cursor pagination (`id > after`), never offset.
- **Resumable batch.** `ingestion_runs.cursor` is saved after every page. A killed or failed run continues from its cursor on the next start; `--fresh` starts over. The quota is spread across a store's feeds (e.g. women/men collections).
- **Polite crawling.** Only `/products.json` and `/collections/<handle>/products.json` (plus `/meta.json` once, for the currency). 1.5 s minimum gap per host, retries with 2/4/8/16 s backoff, honours `Retry-After`, identifying User-Agent. Never `/api/*`.
- **Background work, not in the request path.** Ingestion is a CLI batch (`npm run ingest -- --max 190`). The web page only reads.
- **No secrets in repo or browser.** Tables have RLS on and no policies. The service key stays inside Supabase; batch scripts and the Next.js server talk to the edge function `pipeline` with a token whose SHA-256 hash lives in `pipeline_tokens`. The Vercel token is a sensitive env var (`DRAPE_PIPELINE_TOKEN`). The AI key is not used by the web app.
- **pgvector enabled** (`extensions` schema), no vector columns yet. `gemini-embedding-2` returns 3072 dims by default; HNSW indexes allow up to 2000 dims for `vector` (4000 for `halfvec`), so the classification step should use `outputDimensionality` 1536 or a `halfvec(3072)` column.
- **Models are swappable.** `src/config/models.ts`: `DRAPE_MODEL_CLASSIFIER` (default `gemini-3.5-flash-lite`) and `DRAPE_MODEL_EMBEDDING` (default `gemini-embedding-2`). The REST API accepts the `AQ.` key through the `x-goog-api-key` header.

## Known limits / next scale steps

- Prices are in each store's currency (from `/meta.json`), not converted. Stale offers are trackable via `offers.last_seen_at`, but nothing marks them as gone yet.
- Colour is missing for about 24% of products; the classification step will derive it from the images.
- `/sample` orders by id, so it is grouped by shop. The real feed will use precomputed candidate pools.
- 400 hidden orphan product rows (status `hidden`) remain from the first sample run; delete them when convenient.
- At millions of rows: partition `raw_items` by source or archive old payloads; run `ingest_batch` calls from a queue or cron (Edge Function / Vercel cron).

## Classification (taxonomy v1, tested on one product)

- Taxonomy and strict JSON schema: `src/classify/taxonomy.ts` (`TAXONOMY_VERSION = "v1"`). 10 style weights (0..1, never a single label), category, gender, colors, pattern, material, silhouette, fit, boldness, formality, outfit_role, season, confidence. Output is forced by `responseJsonSchema` and validated again with Ajv.
- Results: `product_classifications` (unique per product + taxonomy version + model, so nothing is classified twice) and `product_embeddings` (`vector(1536)`, L2-normalized, from the product image). Model name and version, token usage, cost and latency are stored with each row.
- One-product test: `npx tsx scripts/classify-one.ts <product_id>`. About $0.0011 and 3.4 s per product (classification + image embedding).

## Image pre-selection and feed readiness (step 2, part 2)

- **Slots.** The feed shows 3 stacked slots: top, bottom, shoes. `feed_slot` is `top` (tops AND outerwear), `bottom`, `shoes`, `full_body` (dresses, jumpsuits, sets) or `none` (accessories). `is_outer_layer` marks jackets/coats worn over another top.
- **Free pre-selection first, AI second.** Every image gets free scores (`product_images`: `bg_whiteness`, `object_fill`, `view_hint`, `score`, `feed_rank`, `selected`): Shopify position, filename/alt hints (front/flat/packshot good; back/detail/model/lifestyle bad), aspect ratio, and a pixel check on a 200px CDN thumbnail (border plainness x brightness, how much of the frame the product fills). The best image is the feed candidate (rank 1), the runner-up is rank 2. `scripts/preselect-images.ts` is idempotent (`analyzed_at`), runs as a backfill over all products and as the step after ingestion for new ones (it only touches unanalysed images). Only ~6 images per product are analysed; all images come from the stored raw payloads, no re-crawl.
- **AI sees one image.** `scripts/classify.ts` reads the queue (`claim_classification_batch`, `for update skip locked`, stale locks re-claimed after 10 min, max 3 attempts) and sends only the pre-selected image plus title/brand to Flash-Lite. If `feed_suitability` < 0.5 (or the JSON is invalid) it retries once with the runner-up and keeps the better result. Idempotent via `product_classifications(product, taxonomy_version, model)` plus an `input_hash`; unchanged inputs are never sent again. A hard cost cap stops the run. Model name/version, tokens and cost are stored on every row. The job is a batch script; nothing in the web app can start it or spend money (the web token is read-only on the gateway).
- **feed_ready.** `feed_ready = !has_model AND !needs_cutout AND feed_suitability >= 0.7` (config `FEED_READY_MIN_SUITABILITY`). Otherwise `image_status = needs_image_work` with `image_reason` = `has_model | needs_cutout | low_suitability`. ALL products are classified (attributes are needed anyway), but only `feed_ready` products are eligible for the feed. Partial index `products_feed_ready_idx (feed_slot, gender, id) where feed_ready`.
- **Later: image work job (not built).** Products with `needs_image_work` get processed by a separate background job (background removal / cutout or regeneration), the result is stored in OUR OWN storage (rights, speed, stable URLs), the product gets a new `feed_image_url`, and `feed_ready` flips to true. Nothing else changes.
- **Embeddings** are made from the final chosen image (1536 dims, L2-normalized) with an HNSW cosine index (`product_embeddings_hnsw_idx`).
- **Cost levers at scale:** Gemini batch mode (50% off), a cheaper model, lower image resolution (`mediaResolution`), context caching for the long static prompt, and classifying each product once.

## Test results: 200 products (taxonomy v2, gemini-3.5-flash-lite), 2026-10-19

- 201 classified (incl. product #10), 0 failures, JSON invalid on the first try in 3 of 303 calls (~1%), always fixed by the single retry.
- Cost: $0.0028 per product incl. runner-up retries (about 50% of products retry), plus $0.00012 for the image embedding. Cheaper `gemini-3.1-flash-lite` (the 2.5 Flash-Lite is closed to new users): $0.0019 per product, same feed_slot/category on 50/50 products, 96% same feed_ready.
- First image rejected by Gemini (suitability < 0.5) for 50% of products; the runner-up was better in 34 of 102 retries. Stores that only photograph on models (Fashion Nova, Armedangels, Gymshark, Outdoor Voices) are 11-44% feed_ready; stores with packshots (Taylor Stitch, Aimé Leon Dore, Kith, Allbirds, Pangaia, Rains) are 73-100%.
- Embedding neighbours (5 seeds) look visually sensible: jackets near shirt jackets/bombers, shoes near shoes, dresses near dresses. They also pick up photo style (Pangaia's warm-grey backdrop).
- Ideas not yet tested: `mediaResolution` low (image tokens are ~half of the input), context caching of the static prompt, skipping the runner-up retry for model-only shops, Gemini batch mode (-50%).

## Packshot stores, cheaper classification, backdrop tone (step 2, part 3)

- **Store selection is data-driven.** A store is only added if `/products.json` works AND a cheap vision check (`scripts/probe-models.ts`, 3.1 Flash-Lite, low resolution, ~$0.0003 per image) finds a model-free image among the first 5 images of most sampled products. Plain background is NOT enough (Mother Denim, AGOLDE, Good American, Studio Nicholson are plain but on models). `scripts/probe-store.ts` shows the gender/category mix. Adding a store stays one config line (`src/ingest/sources.ts`, options `brand`, `defaultGender`, `exclude`, `max`).
- **Default classifier is `gemini-3.1-flash-lite`** (`DRAPE_MODEL_CLASSIFIER` to change) with `mediaResolution: low` (`DRAPE_MEDIA_RES`). Low resolution cut input from ~2,040 to ~1,290 tokens per call: same feed_slot / category / has_model / feed_ready on 50/50 products, pattern 98%, colour 96%, fit 94%, material 92% agreement.
- **Retry policy is derived from data, not hardcoded.** `store_retry_policy()` looks at past classifications per store: if the first pick is rejected (suitability < 0.5) for >= 80% of products and the runner-up helped in <= 30% of the retries (needs >= 12 products), the runner-up retry is skipped for that store. New stores learn this from their first products.
- **Already classified = skipped.** A product with any v2 classification is never sent again (unless `--force`); the input hash also covers prompt revision, model and image resolution.
- **Backdrop tone.** Plain light-neutral backdrops (e.g. Pangaia's warm grey) count as feed_ready. `product_images.bg_color` (median border colour) and `whiten_factor` (CSS `filter: brightness(x)` that turns the backdrop white; capped at 1.3) are stored, copied to `products.feed_bg_color / feed_whiten`. `mix-blend-mode: multiply` removes WHITE backdrops on a coloured page; for a grey backdrop on a white page use the brightness factor.
- **Brand clean-up without changing keys.** `brandKey`/`keyBrand`: the display brand can be renamed (Gymshark) while the canonical key keeps using the old string, so re-ingest never creates duplicates. Existing rows were updated with an idempotent `update ... where brand like 'Gymshark |%'`.
- **Scale levers for the classification job:** parallel workers are safe (`for update skip locked`); cost per product is ~$0.0011-0.0013; Gemini batch mode (-50%) is the next lever for the million-product run.
- **Operational note:** the Supabase MCP tool hangs on destructive SQL (DROP/DELETE/TRUNCATE); migrations are written without them.

About $0.0013 per product. 8,357 products in ~50 min with 2 parallel workers (~2.8 products/s); the data-derived retry policy skipped the runner-up retry for Fashion Nova, Armedangels and Gymshark (~470 saved calls).

## Outfit feed prototype (step 3)

**Flow.** `scripts/build-outfits.ts` (background job) -> table `outfit_pool` (precomputed cache; outfits are NOT a saved unit for users, only products are liked) -> `feed_list()` SQL function -> `/api/feed` (Next route handler, server-side token, rate limited) -> `Feed` (client). Nothing is computed per request.

**Pool (`outfit_pool`).** One row per (gender, top, bottom, shoes); `bottom_id = 0` means a full-body piece (dress, jumpsuit, set) in `top_id` with shoes below. Upserted by that unique key, `run_id` per run, rows not produced by the latest run are set `active = false` (no deletes, re-runnable). Each row has `score`, `style_key` and `feed_order` (the final feed sequence per gender). Only feed-ready, in-stock products with feed_slot top/bottom/shoes/full_body; underwear/swim/sleepwear/house slippers are excluded.
- **Candidate generation** avoids the n^3 blow-up: for every top and every bottom (bottoms are the scarce slot) keep the 10 best partners by a cheap pair score, then pick the 3 best shoes among all shoes with the full rules; full-body pieces get their 6 best shoes. ~65k candidates per gender, 40 s total.
- **Rules (`src/outfits/score.ts`)**: cosine of style_weights between pieces (34%), colour harmony = neutral base + at most ONE accent colour (22% + multiplicative penalty for 2+ accents), formality closeness (16%), season overlap (10%), silhouette balance (18%: no oversized x oversized unless streetwear-like), pattern clash penalty (2+ patterned pieces), at most one statement piece (statement_level >= 0.7), hard rejects: no shared season, warm-only piece (shorts, sandals) next to cold-only piece (coat, fleece, boots), more than one statement piece. Minimum score 0.84. Pieces are also excluded by name (boxers, pyjamas, swim, sleepwear) and a lone vest/gilet as the only top is penalized.
- **Selection** = by score with per-product caps (top 4, bottom 7, shoes 6, full-body 5 outfits). **Order** = weighted shuffle (score^6) followed by a greedy pass: no product repeated within 12 outfits, no same style 3 times in a row, no same store twice in a row.
- **Pages and variety**: the feed is split into fixed pages of 6 outfits (`feed_order` in [6k, 6k+6)); a device's first visit starts on page `hash(device_id) % pages`, afterwards the client sends the cursor (remembered per gender in localStorage). A page with a cursor is identical for every device, so `/api/feed?cursor=` is CDN-cached (`s-maxage=300`, ~0.15 s); only the start page is per device. Query = index range scan on `(gender, feed_order) where active`, ~16 ms for 6 outfits.

**Rendering.** `products.feed_bbox/feed_aspect` (job `scripts/bbox-feed-images.ts`, idempotent) hold the content bounding box of each feed image; the client crops to it with CSS container units so every product fills its slot equally. Backdrops are blended into white with `mix-blend-mode: multiply` plus `brightness(255 / lowest backdrop channel)` (pure multiply cannot whiten a grey backdrop). The next 3 outfits' images are prefetched; the CDN resizes via `?width=`.

**Event log (`events`, append-only, partitioned).** Partitioned by month on `created_at` (`events_pYYYYMM` plus a default partition); `ensure_event_partitions(n)` creates future partitions and must run monthly (cron) - 12 months are created. A trigger forbids UPDATE/DELETE. Types: impression, dwell_ms, like, unlike, tap_product, view_product_click, scroll_past; columns: device_id, product_id / product_ids, outfit_id, slot, feed_index, gender, dwell_ms, client_ts, created_at. Clients batch (20 events or 5 s, `sendBeacon` on hide); `events_append` takes max 100 per call. Indexes: (device_id, created_at), (product_id, created_at), (event_type, created_at) per partition.
- **Plan at scale**: step 4 reads events incrementally (watermark on id/created_at) to update compact per-device taste vectors; old partitions are detached and exported to cold storage (Parquet) after ~3 months while aggregates stay in Postgres; if volume grows, move ingestion to a queue (Edge Function / Kafka-like) and keep Postgres for aggregates. Likes live in `likes (device_id, product_id)` (soft toggle), history is in the log.

**Gateway rights are data.** `pipeline_tokens.allowed_fns` (per token) and `pipeline_rpc_allowlist` (callable functions): adding a function needs an insert, not a redeploy. The web token may only call feed/likes/events/review functions.

**Results (first prototype, 2026-10-20).** Pool: women 3,380 outfits (806 full-body, 2,478 distinct products), men 1,978 (46 full-body, 1,572 products). Dominant styles: women minimalism 27%, quiet_luxury 13%, resort 10%; men classic 40%, minimalism 16%, workwear 14%. Speed: database 16 ms per page; end to end uncached 0.55-0.95 s from outside the EU (several hops), CDN-cached pages 0.15-0.2 s; one 30 s stall was seen once, so the web path now has a 7 s timeout + one retry and the client retries once. Vercel functions run in `dub1` (next to the Supabase region eu-west-1, `vercel.json`).
**Known weak spots / next:** only three of the four slots can be full for men (men's full-body = 46); style mix is skewed (minimalism / classic); a few novelty pieces (ski-print trousers) slip through; some images still carry a faint non-uniform backdrop gradient (a real cutout job would fix it); the gateway adds ~0.5 s per database call from far away, so the long-term fix is a direct, narrowly scoped database role for the web app plus more CDN caching.

## Feed layout v2: outfit collage (visual only)
The outfit is no longer a straight column of three equal slots but a collage on one canvas. Nothing in the database, pool or scoring changed.
- **Files.** `src/lib/layout/config.ts` is the ONE place with numbers (sizes by garment class, margin zone, jitter, overlap ranges, all templates). `src/lib/layout/engine.ts` is a pure function `computeLayout(pieces, template, seed, canvas) -> rectangles` (no React). `src/components/OutfitCanvas.tsx` only draws the result with percentage positions.
- **Sizes.** Garment class comes from the product name (regex, no DB change): top, outer, longcoat, trousers, shorts, skirt, longskirt, shoes, full. Each class has a max width / max height as a fraction of the canvas (trousers ~48% of the height, shoes ~32% of the width, shorts/skirts lower height cap, dresses up to 65%). A piece is fitted into that box keeping its measured content aspect (`feed_bbox`).
- **Templates.** 6 three-piece templates (A-F) and 3 full-body templates (FA-FC), each also mirrored (suffix `m`): 18 in total. The template is picked by `hash(outfit id) % count`; the same hash seeds the small jitter (cluster +-2.5% x / 2% y, shoes +-1.5% x and +-3.5 degrees), so the same outfit always looks the same.
- **Overlaps.** Shoes are placed at the hem of the trousers/dress, overlapping it by 15-25% of the shoe height, z-order above. Top overlaps the waistband by 3-6% (top above bottom). Everything is scaled down if the cluster does not fit, centred and clamped to the canvas.
- **Margin zone.** 18% of the width on one side (the other side in mirrored templates) stays empty on purpose for the accessories column later; nothing is placed there.
- **Interaction.** Each piece is a tap target the size of its cropped box; the topmost piece (z-order) wins in overlaps. One small heart per product sits at the corner of its box with the least overlap. Canvas size follows a ResizeObserver on the scroller (max width 416 px, centred).
- **Debug.** `/?layout=A` (or `FB`, `Cm`, comma list: first match for the outfit kind wins) forces a template; `&debug=1` shows tap boxes, the template id and the margin zone.
- **Image width.** `feedSrc(card, class)` requests a width from the piece's max size and the share of the image its content covers, so prefetch and render use identical URLs.
- **Known limits.** `mix-blend-mode: multiply` lets a trouser colour shine through light shoes where they overlap; some shoe photos have a faint box backdrop that shows over the trousers (both are fixed by the later cutout job); a few "full body" items are really two-piece sets or shirt-dresses and look small.

## Cutouts: background removal of feed images (step "cutout")
Feed images carry the shop's backdrop (a faint box that showed where shoes overlap trousers). A background job now stores a transparent, cropped copy per feed-ready product; the feed uses it when it exists and falls back to the original photo (with the multiply blend) otherwise.
- **Model.** `isnet-general-use` (ISNet / DIS, Apache-2.0) through `rembg` + `onnxruntime` on CPU: free, runs on our side, no API. Chosen by test on 50 shoes + 20 tops/bottoms against `birefnet-general-lite` (MIT): same visible quality and the same guard results, but BiRefNet-lite needed ~12.8 s per image and ~9 GB RAM against ~2-3 s and ~1.8 GB for ISNet on the same CPU. If a shop already delivers a transparent PNG (Allbirds etc.), its own alpha channel is reused and no model runs.
- **Job.** `scripts/cutout/worker.py` (core: `cutout_core.py`, runner: `run_all.sh`). Order shoes, bottom, top, full_body. Work list = DB function `cutout_todo(slot, after, limit, model, version, shard, shards, retry_failed)`: feed-ready products without a result for this (model, version), or whose `feed_image_url` changed (`cutout_src`). So it is idempotent and resumable (kill and restart any time) and never re-processes unchanged products. Parallel: N processes with `--shard i --shards N` split the id space (id % N). Batches of 30: one RPC for the list, parallel downloads, inference, parallel uploads, one RPC `cutout_apply` for the results. A failing batch is retried after 15 s; a failing image is flagged, never blocks the batch. Not in the request path: the web app only reads finished columns.
- **Storage.** Public-read bucket `cutouts`, files `v<version>/<product id>.webp` (transparent WebP, cropped to the content bbox + 1.5% padding, max 900 px long side). The worker has no storage key: the `pipeline` gateway hands out signed upload URLs (`sign_upload`, only for that bucket and path pattern, only for tokens with that right). Supabase serves these with `cache-control: no-cache` (ETag revalidation); a long-cache domain/rewrite is a later optimisation.
- **Columns on `products`.** `cutout_url`, `cutout_status` (`ok` / `failed`, null = todo), `cutout_reason`, `cutout_model`, `cutout_version`, `cutout_quality` (0..1), `cutout_aspect`, `cutout_src`, `cutout_at`. `product_card()` returns `cutout` + `cutout_aspect` only when status is ok and `cutout_src` equals the current feed image.
- **Quality guard** (on the mask, per slot limits in `cutout_core.LIMITS`): foreground area ratio (too small / whole image), fragments (a pair of shoes = 2; specks and strings below 3% of the largest piece are dropped), border touching (product cropped by the photo frame), holes (enclosed regions that are NOT backdrop-coloured; real gaps between straps stay), undecided edge pixels, and recall of strongly non-backdrop pixels (catches cut-off laces, soles, sleeves, straps; shadows are ignored). Small holes are filled, the inside of the shape is forced opaque, the edge is eroded 1 px to avoid a halo. Failed products keep the original image and carry the reason.
- **Feed.** `viewCard()` swaps a product to its cutout (bbox = whole file, aspect = cutout aspect, no multiply) so the layout engine and the tap boxes use the cutout's real box; originals keep bbox + multiply. Debug: `?cut=off` shows the originals; with `?debug=1` a button toggles cutouts on/off live for the same outfit. Product sheet and /likes still show the original photo.
- **Scaling.** The job is CPU bound (~3.5 s per image per core). One 4-core box does about 1 image/s (~4,000/hour); the 6,700 feed-ready images of today take about 1.5-2 hours. For millions of products: the same worker as stateless containers (one per core or per GPU node), N shards by id, queue-style work list from the database (already how it works), new products only (each product once per model version), and a GPU (about 20-50x faster) or a smaller distilled model for the bulk. Storage is ~69 KB per cutout on average (436 MB for 6,519 files, so about 70 GB per million products); lowering MAX_SIDE or the WebP quality shrinks that.

**Results (2026-10-20, model isnet-general-use v1, cost $0):** 6,724 feed-ready shoes/bottoms/tops/full-body products processed: 6,519 ok (96.9%), 205 failed and kept on the original image. Shoes 1,660 ok / 64 failed (16 image 404, 18 photo cropped by the frame, 15 holes, 15 cut_off); bottoms 1,164 / 26; tops 3,233 / 100 (fragments 24, holes 25, uncertain edges 20, cut_off 19, too_small 7, 404 3, empty 1: mostly white tees on white backdrops and striped/checked shirts where the model leaves holes); full_body 462 / 15. Speed: ~3.7 s per image per process (1 CPU thread), 4 processes = ~1.1 images/s; the whole run took about 2 hours including two restarts. 394 feed-ready products with slot `none` (accessories) are not processed.

## Image check, next-best image, pool eligibility (multi-item images)
Some product photos show several items (three tees in a row, stacked garments). We do not try to cut out "the front one"; instead each product image gets a cheap AI check and a failed image is replaced by the next best photo of the same product.
- **Check (`scripts/image-check.ts`, rules in `src/imagecheck/schema.ts`).** Background job, batched (40), parallel (8 calls), resumable and idempotent: the work list is `image_check_todo(slot, after, limit, model)` = feed-ready products whose current feed image has been through the cutout job and has no row yet in `product_image_checks` for (product, image, model). The model sees the cutout (flattened on white) or the original if there is no cutout, at ~512 px with `MEDIA_RESOLUTION_LOW`, strict JSON: `item_count` (a pair of shoes = 1, a clearly-one-product set = 1), `is_single_product`, `defects[]` (hanger, mannequin, cropped, folded, text_overlay, model_visible, other), `confidence`. Default model `gemini-3.1-flash-lite` (`DRAPE_MODEL_IMAGE_CHECK`). Serious defects (config `SERIOUS_DEFECTS`): hanger, mannequin, cropped, text_overlay, model_visible; `folded`/`other` are only recorded. A check fails on `item_count != 1`, a serious defect, or confidence < 0.5. Every result is stored with model name + version, token usage and cost (`product_image_checks`), the verdict is denormalized on `products` (`image_check_status`, `image_check_src`, `is_single_product`, `item_count`, `image_defects`). Hard cost cap: `--cap` (default $6, summed over the whole table, stops the job).
- **Next best image.** `image_check_apply` marks a failed image (`product_images.check_status = 'fail'`; cutout failures mark it too) and switches `products.feed_image_url` to the best remaining candidate by pre-selection `score` (not `model`/`detail`/`back` views, score >= 0.3, never an image that already failed). The cutout job picks the new image up automatically (`cutout_src != feed_image_url`), then the check runs on it. A product with no candidate left gets `image_status = needs_image_work`, `image_check_status = failed` and `image_work_reason` (`multi_item`, `defect:...`, `cutout_failed`, `low_confidence`) and stays out of the pool. A passing check with a failed cutout also triggers the switch (a product without a usable cutout cannot enter the pool anyway).
- **Pool.** `outfit_inputs()` only returns products whose CURRENT feed image has `cutout_status = ok`, `image_check_status = ok` and `is_single_product` (all three tied to `feed_image_url` by their `*_src` columns, so a switched image is excluded until it is cut out and checked). - **full_body.** The item on the left axis (38%), shoes on the centre axis overlapping its hem.
- **Enlargement.** `PIECE_SCALE` 1.13 -> 1.243 (x1.10). - **Data jobs (background, idempotent, once per product and image, resumable).**
  - `presentation` (`spread_front | folded | other`) is part of the image check (`ic2`, `src/imagecheck/schema.ts`, gemini-3.1-flash-lite, low resolution, strict JSON), so new products get it right after the cutout.   - Measurements `scripts/cutout/measure.py` (`measure_core.py`): from the cutout alpha mask, as ratios of the cutout FILE width (content + 1.5% padding): `hem_ratio` (tops) = median width of the run containing the centre line over a band 1%-6% of the height above the lowest centre-line row of the body, so sleeves/cuffs that hang lower or are separated by a gap are ignored; `waist_ratio` (bottoms) = same at the top (2%-10% below the highest centre-line row); `shape_fill` = mask area / bbox area.   - Both go to the feed card (`product_card`: `presentation`, `hem`, `waist`, `fill`, only while they belong to the current image / cutout).
- **Presentation vs geometry (cross-check).** Tops with a compact rectangular mask (`shape_fill` >= 0.90): 54 are `folded` by the model, 19 are `spread_front`; the 12 we looked at were all folded button-down shirts the model called spread. Bottoms: the mask fill does not separate folded from spread (both 0.75-0.90); by aspect >= 0.8 there are 57 "geometry says folded, model says spread" cases, all of them looked like swim bottoms, shorts and wide trousers, i.e. correct as spread; so no geometry override for bottoms.
- **Outfits in the pool by layout:** men 1,683 stacked / 159 folded / 48 full_body; women 2,445 stacked / 44 folded / 791 full_body. Stacked pairs without both measurements (equal-width fallback): men 197, women 457.

With a clamp of 0.6-1.7 the match would be exact for 350 of 374 (94%). The clamp is the user's choice, so it stays at 0.75-1.35 (`RULES.ratioClamp`).

## Swap a piece (swipe sideways)
- **Alternatives (background job).** `scripts/build-alternatives.ts` fills `outfit_alternatives(outfit_id, slot_key, rank, product_id, score, scorer_version, active)` (slot keys top | bottom | shoes | acc1..3; `top` is the dress in full-body outfits) and `outfit_alt_state(outfit_id, input_hash)`. Up to 6 alternatives per slot, ranked with the outfit builder's own `scoreOutfit` (style, colour, formality, season, silhouette, pattern, one statement piece, hard season/weather rules), with the other pieces fixed. Hard rules: same gender, feed-ready with clean cutout and measurements, not in the outfit, same presentation class (folded stays folded), the outfit's accessories must still pass their rules, no two alternatives of the same brand in a row where possible. Accessories: same `accessory_type` first, other types only if fewer than 3 (exclusivity rules: one head item, one bag, one neck item, one statement piece, accent colour). Idempotent and resumable: an outfit is only recomputed when the hash of its pieces, accessories, the eligible candidate set and the scorer version changed (`--force` overrides). Result: 5,161 of 5,170 outfits covered, 24,734 slots, 5.98 alternatives per slot on average, 61 slots with fewer than 3 (37 tops, 24 bottoms); scorer version `alt2` (a bottom is replaced by a bottom of the same length class).
- **Lookup.** Gateway function `alternatives_list(outfit, slot)` (also allowed for the web token `vercel-sample-page`), route `/api/alternatives` (CDN cache one hour). The browser fetches on the first swipe on a piece, loads the new piece's image BEFORE the swap and prefetches the next ones. State is in memory only (`src/lib/client/swap.ts`): swapped pieces stay while the user scrolls back and forth, reset on reload.
- **Gesture.** Pointer events on the outfit canvas with `touch-action: pan-y`: a drag counts as a swipe only if it starts on a piece (topmost piece under the finger, so shoes / overlays win), moves more than 14 px, mostly horizontally (|dx| > 2 x |dy|) and ends at least 44 px away; a vertical drag (|dy| > 12 and |dy| > 0.7 |dx|) cancels it, so scrolling is unchanged. Left = next alternative, right = previous (back to the original). End of the list: small bounce, nothing else. The tap that follows a drag is suppressed. The layout is recomputed by the normal engine (pieces animate to their new positions), the old piece slides out and the new one slides in.
- **Events.** New append-only event type `swap` (ctx: out = product that left, dir = next|prev, rank = alternative rank, 0 = original; product_id = product now shown; slot; feed_index). Hearts, taps, impressions and dwell use the piece currently shown. Not used for ranking yet.

## Swap loop of three, preloading, SALE label
- **Loop.** Every swappable piece has exactly the original + 2 alternatives (ranks 1 and 2 of `outfit_alternatives`). The builder (`alt3`) picks rank 1 = best and rank 2 = the best other candidate that is visibly different from it (other brand, other main colour, style similarity < 0.96; the conditions are relaxed step by step if nothing qualifies); ranks 3-6 stay for later. Swipe right = next, left = previous, both loop forever (original -> 1 -> 2 -> original); no bounce. Later personalization can pick the 2 alternatives per device from the stored 6.
- **No request on swipe.** `feed_list` returns `alts` per outfit (slot key -> the 2 alternatives as null-stripped cards, accessories with their type / size / front_flat / belt_shape, plus `slot_no` on the outfit's accessories). The pages stay CDN-cacheable (cursor pages are identical for everyone). The swipe never calls `/api/alternatives` (the endpoint stays for later use). Extra size: about 1 KB gzipped per outfit (6 outfits: 10.6 KB gzip vs 4.5 KB without alternatives).
- **Preloading** (`Feed.tsx`): 700 ms after an outfit is fully shown, in idle time (`requestIdleCallback`), `fetchPriority = low`, same image sizes as the main pieces; order: the visible outfit's top / bottom / shoes alternatives, then its accessory alternatives, then the next outfit's first alternative per main piece; cancelled (in-flight images aborted) when the user scrolls on; skipped with `navigator.connection.saveData` or 2g; `?preload=off` switches it off for tests.
- **Measured** (headless Chromium, slow 4G 1.6 Mbit/s + 150 ms RTT, CPU 4x, so not a real phone): finger up -> new piece on screen: with preloading, first swipe 61 ms, later swipes 20-34 ms (8 s after the outfit appeared); first swipe 131 ms when the swipe comes 1.5 s after the outfit appeared, but the second piece swapped then waited up to 730 ms for its image (slow 4G cannot load 10 images in 1.5 s); without preloading 430 ms for the first swipe, up to 760 ms for shoes. From touch start the numbers are about 400 ms higher because the scripted drag itself takes that long under CPU throttling. Data: roughly 1 MB of images for the current + next outfit when the user stays (tiered, so less if they scroll on); +1 MB over 20 outfits viewed for 1.5 s each. Scroll smoothness over 20 outfits (450 ms scroll + 1.5 s pause each): preloading off mean 16.5 ms / p95 16.8 ms / 5 frames over 33 ms; on mean 16.8 ms / p95 16.8 ms / 8 frames over 33 ms (about +0.5% of frames, within noise for this test).
- **Events.** `swap` ctx: `out` (product that left), `dir` (next / prev), `rank` and `alt` (loop position now), `from` (loop position before); 0 = original, so swapping back to the original is logged too.
- **SALE label.** `SALE_LABEL` in `config.ts` (font size 3.2% of the canvas width = 12.5 px on a 390 px phone, about 9 px cap height, the same for every product). Font Permanent Marker (`next/font/google`, variable `--font-marker`), colour #e0221b, one object, `writing-mode: vertical-rl` + 180deg rotation (reads bottom to top), no bending. It sits on the side of the piece's box (side away from the other pieces first, then the other one) with a gap of 1.6% of the width to the outline, vertically centred on the piece, and is skipped if neither side is free of other pieces, the 2.5% margin or the canvas edge. It is a child of the piece's button, so it moves and animates with swaps and follows the swapped-in piece's sale state. Same switch as the outline (`SALE_MARKER_ENABLED`, `?sale=on|off`).

## Dynamic composer spike (prototype, `?feed=dynamic`; default feed and `outfit_pool` untouched)
**Idea:** only a small starter set is prebuilt; after that outfits are composed while the user scrolls, from an in-memory catalogue, with a per-device taste profile and ban list. Guests use the same composer with a neutral profile (95% "new", about 5% deliberate contrast).

**Reused (unchanged behaviour):** `toPiece`, `scoreOutfit`, `outfitStyle` (score.ts: same minimum 0.84, same hard rules), the pool builder's pair scoring / shoe choice / ordering rules (now extracted to `src/outfits/pool-shared.ts`: `pairScore`, `bestShoes`, `candidatesFor`, `select`, `order`, `StreakGuard`; `scripts/build-outfits.ts` imports them, its output is byte-identical to before: checked with a dry run before and after), `chooseAccessories` / `outfitCtx` / `placementFor` (accessories.ts), the layout engine (as validator), `product_card` shape, the swipe-loop UI, the swap pair rule (`pickPair`, extracted to `alt-shared.ts`, used by the stored-alternatives job too). **New:** `catalogue.ts`, `season.ts`, `compose.ts` + `compose-config.ts`, `ban.ts`, `taste.ts`, `compose-alts.ts`, `starter.ts`, `src/lib/dynamic.ts`, `/api/dynamic`, tables `catalogue_snapshot`, `device_bans`, `starter_outfits`, RPCs `composer_inputs`, `snapshot_put/get`, `ban_get/put`, `starter_put/list`, `cards_by_ids`, jobs `build-catalogue.ts`, `build-starter.ts`, and the simulation scripts in `scripts/spike/`.

**1. Catalogue in memory.** Snapshot job (`scripts/build-catalogue.ts`) merges classification (`outfit_inputs`, `acc_inputs`) with `composer_inputs` (brand, cutout aspect, hem / waist / collar / hood, presentation and the card display fields) into one gzip+base64 blob in `catalogue_snapshot` (version = hash of the content; unchanged content is not stored again). Measured: 4,973 feed-ready main pieces + 2,166 accessories, blob 906 KB, unpack + build 224 ms, heap +11 MB (process heap 42 MB, RSS 144 MB including Node and tsx), typed columns (vectors in one Float32Array, formality / boldness / statement / season / slot / gender) and indexes by (gender, slot) and (gender, slot, season). Per function instance: `getCatalogue()` keeps it in module memory and asks `snapshot_get(version)` at most every 5 minutes; "unchanged" costs one tiny call. Cold start on Vercel: about 2.5 s for the first request (snapshot fetch through the gateway + build), then warm. **Scale path (not built):** at millions of products the catalogue no longer fits one instance per gender; keep the per-slot candidate retrieval in pgvector / an ANN index with filters on gender, slot, season (and formality bucket), fetch a few hundred candidates per slot per page, and run the same scoring on those; the composer already works on candidate lists, so only `cand()` changes. Hot slices (season x gender) can stay cached.

**2. Season of an outfit** (`src/outfits/season.ts`, pure, no column): intersects the season lists of the pieces, weights decisive pieces (outerwear 2.5, shorts / boots / sandals / beanie / scarf / gloves 2, sunglasses 1.5, light jacket 2), picks the most specific season when several remain (spring+summer -> summer with shorts / sandals / tank, spring with a light jacket, otherwise summer; autumn+winter -> winter with coat / beanie / scarf / gloves / boots), "all" only when nothing carries a season, returns a fit 0..1 (share of the vote, how few seasons are left, decisive pieces backing it). Neutral accessories (bag, belt, watch, jewellery) only vote; they never narrow the intersection (found with the first samples: a tote tagged spring+summer+autumn turned a winter outfit into autumn). Honest limits: the classifier's season lists are coarse, intersections often keep two seasons so fit rarely exceeds 0.78; ambiguous cases (a mini dress with penny loafers = spring or autumn) get a low fit instead of a confident wrong answer.

**3. Composer** (`compose(cat, profile, ban, n, session, rnd)`): per outfit it draws a bucket (match / near / new / contrast; shares in `compose-config.ts`), a target season (current season 40%), an anchor slot by weight (full-body weight = its share of the catalogue), an anchor piece by taste band x freshness, fills the other slots (pair proxy `pairScore`, then the full `scoreOutfit` >= 0.84), chooses by weighted sampling among the best 12 (score^6 x taste x connection bonus x freshness), then accessories with `chooseAccessories`, then validators: layout (the real engine must lay it out without dropping a piece and inside the canvas), bottom length vs shoes (short bottoms never with boots), session streaks (`StreakGuard`: no product repeated within 12 outfits, no third equal style in a row, no equal store in a row), cutout and measurements (guaranteed by the catalogue filter). Contrast patterns: smart shoes + relaxed bottom, tailored bottom + sporty shoes, formal top + relaxed bottom, sporty top + tailored bottom (own minimum score 0.80, up to 7 retries of the pattern). Likes use the same ban treatment as other pieces (`COMPOSE.likesBanned`, `profile.likedIds` to let liked pieces return later).

**4. Ban list.** Per device a list of served single products (int32, oldest first, at most 1,000 = 3.9 KB). A product enters at composition time. Limit per group (slot, accessory type): at most 40% of the group is banned at once (`COMPOSE.ban.fraction`), at most 1,000 ids overall; soft fallback: if fewer than 12 allowed candidates (4 for accessories) are left, the OLDEST bans are released first (`allowed()`), so the feed never empties. **Simulation** (one guest device, 504 outfits, `scripts/spike/sim-ban.ts`): banned share after 504 outfits, men: tops 12%, bottoms 40%, shoes 28%, gloves 40%, rings 30% (the naive single limit of 1,000 gave bottoms 45%, gloves up to 85% at 168 outfits); women: tops 10%, bottoms 23%, shoes 16%, gloves 39%, rings 39%. Score median stays flat (men 0.880 -> 0.884, women 0.878 -> 0.877), unique pieces per 84 outfits stay at 84 / 84 / 84 (women's shoes 58-84: the shoe pool is the narrower one), 0 repeats of a product within 100 outfits, soft fallback released bans in 1 of 3,494 slot lookups (men) and 84 of 3,236 (women, accessory groups). **Recommendation:** 40% per group and 1,000 overall as configured; 25% also works and keeps even small groups usable (gloves 38, rings 46) at no quality cost, so go lower if small accessory groups feel empty. **Storage:** the default is a ban list held by the client (localStorage, sent with each page request, 4-5 KB) because it needs no database at all (0 ms, nothing to clean up, free at any scale; a user who clears it only resets a recommendation filter). Database copy (table `device_bans`, bytea, `?ban=db`): measured read 335 ms + write 349 ms per page through the gateway (so total server time per page 787 ms instead of 106 ms); at 1 million devices about 4.2 GB, and 20 million page writes per day rewrite a 4 KB row each (about 80 GB of WAL per day): too heavy for Postgres. Redis / KV (Upstash, Vercel KV): about 4 GB of RAM at 1 million devices, 5-20 ms per call in-region, `EXPIRE` for inactive devices (30 days) for free; cost is per request (2 commands per page, about 40 million per day at 1 million daily users x 20 pages, roughly the same order as the compute cost) or a fixed plan; use it when the ban list must survive across devices / logins. Postgres cleanup would need a job on `device_bans_updated_idx`.

**5. No outfit storage.** A composed outfit is a list of piece ids. `outfitHash` = 52-bit hash of the sorted `slot:id` list (accessories included), always >= 2^51 so it never collides with pool ids, which are small integers. Design choice: the existing `events.outfit_id` (bigint) simply takes the hash (verified: an `outfit_up` and a `swap` with an id of 2^51 + 2 were stored; the route's limit for outfit_id was raised to 2^53), and the events that matter already carry the piece ids (`product_ids` on impression / dwell / outfit_up / outfit_down / scroll_past, `product_id` on tap / like / swap with `ctx.out`). So the log works without an outfit table and without a schema change; the same outfit shown twice has the same id, which makes "same outfit liked again" analysable. Season and other properties are computed on demand with the shared functions; aggregates would be stored lazily (get-or-create on the first like or `outfit_up`) only if analysis needs them. The browser keeps every shown outfit in memory (the list is the session), so scrolling back works; a reload starts a new session.

**6. Starter set** (`scripts/build-starter.ts`, table `starter_outfits`, served by `GET /api/dynamic?starter=<page>`, CDN `s-maxage=600`): 60 outfits per gender curated from 24 x 14 composer pages (about 2,000 candidates per gender, minimum score 0.90, 5% contrast = 3, no product used twice, style quota with a cap of quota+3, ordered with the pool's own weighted shuffle + streak rules). Style spread, women: 18 styles with supply, quota 3 each (quiet_luxury 6), contrast 3; styles without supply: western. Men: 12 styles (minimalism, business_casual, athleisure, workwear, gorpcore 7 each; classic, streetwear, sporty, old_money, vintage 4; preppy 1, retro_sport 1), contrast 3; without supply: techwear, scandi, quiet_luxury. After the starter set the client switches to `POST /api/dynamic` with `startersServed`; the server puts the starter pieces into the ban list first, so nothing repeats.

**7. Taste profile and connections** (`src/outfits/taste.ts`, prototype, driven by simulated events, not wired into the live app). Per device (about 5.3 KB): style vector per slot (24 styles), colour / silhouette / category preferences, running formality and boldness, two style x style connection matrices (top x bottom, bottom x shoes), a formality-gap histogram and hashed category pairs. Learned incrementally from like, tap, view_product_click, dwell, scroll_past, outfit_up / outfit_down and swap (`from` piece weak negative, `alt` piece weak positive, going back to the original positive for it; a swap is an implicit signal, never a dislike), with decay 0.995 per event. **Why attribute level and not per product pair:** there are millions of possible pairs and each one is seen once or never, so there is nothing to learn from and a new product has no history; style / attribute connections generalise to every new product at once, fit in a fixed few KB per device and update in O(24 x 24) per event. Demo (`scripts/spike/taste-demo.ts`, 40 pages for the persona "smart bottoms + relaxed tops", men): strongest top x bottom connections classic x classic, classic x business_casual; formality gap concentrated in bins 0-1; the model learned "classic / business casual / minimalism" for all slots; it did NOT learn "relaxed top + smart bottom" as a distinct pattern because the men's catalogue has almost no relaxed streetwear tops that pass the score with tailored bottoms (supply, see below). **Sketch of the table and the job:** `device_taste(device_id uuid primary key, taste bytea /* the structure above, float16 would halve it */, n_events int, last_event_id bigint, updated_at timestamptz)`; an incremental job reads `events` with `id > last_event_id` per device (index `events_device_time_idx`), resolves piece ids to catalogue rows, calls `applyEvent`, writes the row; replays are skipped by the watermark (`applyEvent` ignores `id <= lastEventId`), so the job is idempotent and resumable.

**8. Swap alternatives from the composer** (`compose-alts.ts`): rest of the outfit fixed, same slot, same presentation class and bottom length class, accessories must still pass their rules, ban list applied softly, visibly different pair (`pickPair`). Comparison on 400 random pool outfits (`scripts/spike/alts-compare.ts`): outfit score of the replaced outfit, composer vs stored: top median 0.937 vs 0.935, bottom 0.926 vs 0.925, shoes 0.934 vs 0.933; share >= 0.84 100% vs 99-100%; pair different in colour + brand (0-2) 1.87-1.93 vs 1.86-1.93. Same quality. The dynamic feed delivers them inside the page like the stored ones.

**9. Benchmarks** (honest numbers, and where they ran). *Node 22, sandbox* (`scripts/spike/bench.ts`, 150 pages per case): compose 6 outfits p50 9-12 ms / p95 15-18 ms for guests, 24-27 ms / 41-51 ms with a taste profile; the 2 alternatives for all pieces of 6 outfits p50 18-27 ms / p95 30-40 ms. *Vercel function* (live `/api/dynamic`, 12 warm requests): compose + alternatives p50 82-99 ms (the instance is slower than the sandbox), server time per page 106 ms with the client-held ban list (target 150 ms met), 787 ms with the database ban list (335 ms read + 349 ms write through the gateway; this is the number that breaks the target, not the compute). The first request after a cold start takes about 2.5 s (catalogue load). DB / KV round trips per page: catalogue 0 (cached per instance, one version check every 5 minutes), ban 0 (client-held) or 2 (database), taste 0 in the prototype (would be 1 read + 1 write per page, or client-held like the ban list), cards 0 (built from the snapshot; before that a `cards_by_ids` call cost 400-525 ms, so the snapshot now carries the card fields; price and stock follow the snapshot version), events unchanged. Memory per instance about 11 MB for the catalogue. **Cost** (estimate from Vercel's published Fluid-compute rates, not billed data): about 0.1 CPU-second per page is roughly 0.004 USD per 1,000 pages; 1 million daily users x 20 pages = 20 million pages per day, about 75 USD per day (about 2,300 USD per month) of function compute, plus the KV cost if a KV store is used. The pool path is a cached read: near zero per page and constant. **Keeping per-device compute small:** cache candidate lists per taste cluster (for example 50 clusters x gender x season x slot, refreshed with the snapshot) so the per-device part is only sampling + ban filtering + scoring of a few dozen pairs; serve guests and cold-start devices from CDN-cached pages (starter set or pool pages) and compose only for devices with enough events; compose the next page while the user looks at the current one (prefetch).

**10. Quality** (`scripts/spike/quality.ts`: per gender 5 personas + guest, each persona first scrolls 10 guest pages with simulated reactions, then 100 composed pages = 600 outfits). Score >= 0.84: 97-99% of all outfits and 100% of the non-contrast ones (contrast outfits start at 0.80); score median 0.865-0.891 (p10 0.843-0.848) against the old pool 0.940 (women) / 0.923 (men): the composer is about 0.05 lower in median because it samples (160 partners, 140 shoes, weighted among the best 12) instead of keeping the best of 58,000 candidates. Unique pieces in 600 outfits: tops 493-548, bottoms 313-357, shoes 356-477 (the old men's pool: 742 tops, 337 bottoms, 427 shoes in 1,865 outfits). Product repeats within 300 outfits: women 145-293, men 338-444 (bans last about 0.4 x group size outfits, so small groups come back by design). On-style share (persona affinity >= 0.5) vs the old pool: smart bottoms + relaxed tops 71% vs 43% (women) and 65% vs 51% (men); streetwear 9% vs 4% / 11% vs 6%; old money 57% vs 29% / 55% vs 38%; minimal / scandi 74% vs 45% / 53% vs 32%; sporty / gorpcore 26% vs 10% / 20% vs 12%; guest: no profile. Streetwear and sporty stay low because supply is thin (see below), not because the composer ignores them. Contrast share reached 2-3% (target 5%) because many contrast attempts fail the score; validators: 1.3-1.7 attempts per outfit, attempt-level failures 25-42% (women 25-29%, men 32-42%), mostly "no candidate" and "streak" (the men's catalogue is classic-heavy, so the style / store streak rule bites), layout failures 0-12 in 600 (at most 2%); the "bottom length vs shoes" filter removed 80-180 shoe candidates per persona run. Season mix of the output is even across the four seasons. Real screenshots through `?feed=dynamic&starter=off` at 390x844 and 360x740 (12 women, 12 men, 8 contrast): no layout errors; the pieces and accessories render like the pool outfits, the sale marker and labels work. **What looks odd / worse than pool outfits:** (1) less polish in the score tail (more outfits near 0.85 than the pool's 0.94 median); (2) women's pages are dominated by athleisure / hoodie + sweatpants outfits because that is the supply; (3) the contrast patterns often look like ordinary outfits (sneakers with tailored trousers) because few pieces are strongly sporty or strongly formal; (4) colour-on-colour sets (pink hoodie + pink sweatpants) appear; (5) a few accessory combinations repeat (several bags and caps from the same shops). **Styles that lack supply** (dominant style, pieces tops / bottoms / shoes): women: techwear 1/2/0, skater 0/0/2, grunge 0/0/0, dark_academia 2/0/2, punk_edgy 2/0/6, western 7/6/17, boho 9/15/1, retro_sport 9/1/14, and bottoms or shoes for old_money 41/4/33, preppy 78/8/8, scandi 37/13/5, business_casual 25/21/6, vintage 60/15/7; men: techwear 0/2/0, y2k 0, skater 0, grunge 0, coquette 0, boho 0, punk_edgy 0, western 3/0/4, dark_academia 7/4/0, scandi 11/0/3, quiet_luxury 14/3/1, retro_sport 6/1/11, and bottoms or shoes for preppy 76/4/1, vintage 52/7/3, business_casual 35/12/2, streetwear 158/12/52, old_money 58/9/27, sporty 17/6/25.

**11. Recommendation (simple words).** Hybrid. Use the starter set and the existing pool-style cached pages for guests and the first minutes (cheap, fast, best quality), and the composer for devices that have shown taste (about 20+ events): it gives the personalization step a place to act (taste, connections, bans, swaps) without a pool rebuild, uses far more of the catalogue (about 500 different tops in 600 outfits instead of reusing the same pool) and keeps quality close to the pool. Do not replace the pool completely yet: the composer's median score is about 0.05 lower, the page costs real compute (about 0.1 s of CPU, roughly 75 USD per day at 1 million daily users) and it needs a client-held or KV ban list to stay under 150 ms. **For step 4:** build the `device_taste` update job and the client-held ban list first, make the composer read the taste for devices with enough events, keep the pool as fallback and for guests, compose the next page in advance, raise sampling (more partners / shoes) only where the score tail matters. Effort: about one to two weeks for taste job + live wiring + KV decision; risks: season lists are coarse (fit values stay low), thin supply in many styles limits what personalization can show, per-request compute needs the cluster cache before big traffic. **Proposed wording for the scalability line in CLAUDE.md** (not changed yet), replacing "Fast feed. Feed requests use precomputed or cached candidate pools, indexed queries and cursor pagination. No full-table scans, no heavy computation per request.": "Fast feed. A feed page is either precomputed / CDN-cached (starter set, guests, pool pages) or composed on demand from a versioned in-memory catalogue snapshot kept per function instance (no database read per page except small per-device state such as a taste vector; no full-table scans; budget under 150 ms per page; never a paid service call). Catalogue, candidate lists and alternatives are refreshed by background jobs; per-device state (taste, ban list) is small, incremental and expires when inactive."

## Cost explanation for the dynamic composer (replaces the one-line "$75 per day" estimate)
**Sources and date.** Vercel docs "Pricing on Vercel" (page last updated 2026-09-14) and "Fluid compute pricing" (last updated 2026-06-16), Supabase pricing page; all read on 2026-10-21. List prices, Pro plan, no discounts, no included credit counted. Our functions run in `dub1` (Dublin): Active CPU $0.168 per hour, provisioned memory $0.0139 per GB-hour, invocations $0.60 per million (the earlier "$75" used the cheaper US rate of $0.128 per CPU-hour and counted only CPU; that was an incomplete number). Other rates used: Fast Data Transfer $0.15 per GB, CDN requests $2.00 per million, Supabase Edge Function invocations $2 per million beyond 2 million per month, egress $0.09 per GB beyond 250 GB, DB compute add-ons $15 / $60 / $110 / $210 per month (Small / Medium / Large / XL).

**Assumptions (measured where possible).** One composed page = 6 outfits = one `POST /api/dynamic`: server time 106 ms (measured on Vercel with the client-held ban list; treated as 0.106 s of Active CPU, which is generous because part of it is waiting), 1 GB provisioned memory held for that time (assumption), response 12.9 KB gzipped (64.7 KB raw, measured), request 1.6 KB. Each page also causes about 1 events request (15 events per page, batched; assumption). 1 million daily users x 20 pages = 20 million pages per day. Images: 64.7 KB average per cutout (measured over 10,026 files), about 5 images per outfit (3 main pieces + about 2 accessories), plus the swap preloading (about +0.5 MB per page if the user stays).

**Per 1 million pages (composer function path, no images):** Active CPU 0.106 s x 1M = 29.4 CPU-hours x $0.168 = $4.95; invocations 1M x $0.60/M = $0.60 (+ $0.60 for the events call); memory 29.4 GB-hours x $0.0139 = $0.41; page response transfer 12.9 GB x $0.15 = $1.94; CDN requests (page + events) 2M x $2/M = $4.00. **Sum about $12.5 per million pages** (about $0.0125 per 1,000 pages).

| Daily users (20 pages each) | pages / day | composer function path / day | images / day (same for the old pool!) |
|---|---|---|---|
| 1,000 | 20 thousand | about $0.25 | about $8.4 (48 GB + 0.6 million image requests) |
| 100,000 | 2 million | about $25 | about $840 |
| 1,000,000 | 20 million | about $250 (CPU $99, invocations $24, memory $8, page transfer $39, CDN requests $80) | about $8,400 |

**Supabase for composing:** 0 database reads or writes per page with the client-held ban list (catalogue snapshot = one 906 KB read per cold start, a few dozen per day, negligible; with the database ban list it would be 2 gateway calls per page = 40 million edge-function invocations per day = about $80 per day more at 1 million users, and a 4 GB table with 20 million row rewrites). **What does cost Supabase is the event log, and it is the same for the pool and the composer:** about 15 events per page = 300 million rows per day at 1 million users (3,500 inserts per second, about 60 GB per day), one edge-function invocation per events batch (about $40 per day beyond the included 2 million per month) and a database compute size of XL or larger plus archiving / sampling of old partitions; this must be planned in step 4 either way.

**Images are the largest item and do not depend on the composer.** About 5 images x 64.7 KB x 6 outfits = 1.9 MB per page plus preloading, about 2.4 MB: 48 MB per user and day = 48 TB per day at 1 million users = $7,200 of Fast Data Transfer plus about 600 million image requests = $1,200. The pool feed has the same image cost. Mitigations (not part of this spike): longer browser cache (already immutable), smaller WebP sizes per device, the Vercel Flat Rate CDN tier, or serving images from a zero-egress store / CDN (Cloudflare R2, Bunny) instead of Vercel transfer.

**Effect of caching per taste cluster.** The per-device compute can be cut because candidate lists, pair scores and the 2 alternatives per piece depend on the taste cluster (about 50 clusters x gender x season), not on the device; only ban filtering and sampling stay per device. Estimate: CPU per page 106 ms -> about 25 ms (the sampling part measured in Node was about 10 ms for 6 outfits; the rest is the alternatives and the scoring that a cluster cache replaces), so CPU $99 -> $25 and memory $8 -> $2 per day at 1 million users (function path $250 -> about $170 per day). If whole pages are CDN-cached per cluster and season for the first pages of a session (like pool pages), those pages need no invocation at all (saves invocations, CPU and memory, about $130 per day) but still count as CDN requests and transfer. So even with clusters the composer path stays in the low hundreds of dollars per day at 1 million daily users, an order of magnitude below the image delivery.

**No paid AI or API call happens when composing.** The composer reads the in-memory catalogue and does arithmetic (`scoreOutfit`, sampling, layout check); `src/outfits/*` and `src/lib/dynamic.ts` contain no network call except the Supabase gateway (snapshot, optional ban copy, starter list), and no AI key is available to the web app. AI cost only occurs in the background jobs when NEW products are classified (about $0.0011 per product with gemini-3.1-flash-lite at low resolution, about $0.0003 for a hood check) and in the image check; both are capped per run and triggered only with a pipeline token, never by public traffic.

## Composer polish and cost guards (2026-10-21, all behind ?feed=dynamic; the default feed and the pool are unchanged)

## Step 4: personalization as a hybrid (?feed=hybrid, 2026-10-22)
**What it is.** New devices get the starter set (CDN-cached pages), then the composer with a neutral profile (95% "new", 5% deliberate style breaks). From 20 signals on (`TASTE.personalizeFrom`) the composer personalizes with the device's taste. The default feed (pool) is unchanged; `?feed=base` forces it, `?feed=dynamic` is the plain composer, `?feed=hybrid` the new path. Nothing paid in any request; no database read or write per page for the taste.
**Taste model** (`src/outfits/taste.ts`, weights in `src/lib/personalization/config.ts`): per device and gender, per slot (top, bottom, shoes) a POSITIVE and a NEGATIVE style vector over the 24 styles (kept apart: in the first simulation one combined vector let many weak negatives push common styles below never-seen ones, so the taste "learned" y2k / punk for a minimal persona), attribute preferences (colours, categories, silhouettes as decayed signed sums, formality and boldness as running means), tag preferences (season, occasion, palette kind, silhouette, formality level, weather, contrast), connections (style x style top-bottom and bottom-shoes 24x24, formality-gap histogram, 64 hashed category pairs), signal counts and watermarks. Decay 0.995 per event (half-life about 140 events). Taste match of a piece = 0.75 x (cos(positive) - 0.5 x cos(negative)) + 0.25 x attribute match; composer sampling weight = (0.2 + 0.8 x match)^2; final pick x (1 + 0.35 x tag match) x (1 + connection bonus).
**Signal weights** (config): like +1.0 (its outfit's combination x0.6), unlike -1.0 (reverts), view_product_click +0.8, tap_product +0.4, dwell up to +0.3 (from 3 s, full at 10 s), scroll_past -0.15 on every piece, outfit_up +0.6 on every product (+0.8 on the combination), outfit_down -0.35 per product (-0.6 on the combination; smaller per product than up), outfit_clear takes the previous up / down back, swap: the piece swiped away -0.25 on its own attributes only, the piece swiped in +0.1, going back to the original +0.2, the piece on screen when the user leaves a swapped outfit counts as kept +0.15 (x2 after a like / tap / long look). Tags move by 0.5 x the event weight. A negative also takes back up to half of its weight from the positive side of that style. No dislike button: likes belong to products, outfits are never saved.
**Event payloads (checked live and in the database):** outfit_up / down / clear, swap, tap_product, like / unlike and now dwell_ms carry the compact tags in `ctx.tags`; like / unlike events now also carry the outfit's product ids (the combination behind a like, for replay).
**Where the taste lives (decision: client-held).** Measured: (a) client-held: the browser keeps the taste (base64, int16-quantized + deflate: 4.2-4.7 KB after 100 signals; it was 5.8 KB as float32) and an outbox of signals (the same events that go to the event log, about 60-120 bytes each, at most 80). The page request carries both (about 5 KB), the server applies the outbox with the shared pure `applyEvent` (it holds the catalogue features in memory; the browser does not, so the update runs server-side at page time - which is also the only moment the taste is used), composes and returns the updated taste. Cost: +1.3 ms server time per page (decode, apply 15 signals, encode), about +9 KB transfer per page (5 KB up, 4.2 KB down), 0 database operations; at 1 million daily users x 20 pages = about 184 GB per day = about $28 per day of transfer at $0.15 / GB if both directions are billed. (b) server-side `device_taste` in Redis / KV (Upstash pay-as-you-go $0.20 per 100k commands, storage $0.25 / GB, read on 2026-10-21): 2 commands per page = 40 million per day at 1 million users = about $80 per day (plus 5 GB storage, about $1.25 per day), 5-20 ms per command in the same region (10-40 ms per page unless pipelined), plus an idempotent batch job reading new events per device since its watermark (`events_for_device` uses the (device_id, created_at) index; partitions by month, archiving of old events and a TTL for inactive devices). (b) is the documented option for when a login needs one taste on several devices. **The event log stays the source of truth:** `scripts/replay-taste.ts` (and `GET /api/taste?device=`) rebuild the taste from `events` with the same function (`eventsToSignals` derives "keep" like the client does); incremental with `--since` on top of an existing taste. Failure modes: cleared browser = taste and device id are gone (a new device; with a login the replay restores it); manipulation of the taste or outbox only changes the own feed (validated: size limits, known types, finite numbers); a corrupt or old-format taste is ignored (new neutral taste).
**Hybrid logic** (`src/lib/dynamic.ts`, `src/components/Feed.tsx`): the client counts taste signals + outbox; under 20 it walks the starter pages (GET, CDN), then POSTs; from 20 on it POSTs right away. Mix for a personalized device (config `MIX.personal`): 47% match (top 15% taste band), 28% near (next 35%), 20% new (exploration, never below 18%), 5% style breaks; the ban list is unchanged (25% per group, 300 overall, client-held, soft fallback). **Thin supply:** the bands are percentiles of the taste match, so a taste that points to a thin style automatically gets the nearest styles (cosine); styles with fewer than 15 pieces per slot are reported (`stats.thin`; simulation: men's y2k / punk bottoms, techwear shoes, business-casual shoes, women's old-money bottoms). **Swap alternatives** are re-ranked by taste (score x (1 + 0.12 x (match - 0.5) x 2), still a visibly different pair); first swipe on the live site: new piece visible after 12-23 ms (unchanged, alternatives come with the page and are preloaded).
**Latency (Vercel, warm, 20 requests):** hybrid personalized server time p50 94 ms, p95 104 ms (compose + alternatives p50 93 ms; taste 1.3 ms); plain composer p50 81 / p95 112 ms. In the sandbox the first version took 211 ms for compose alone: the taste match of each piece was recomputed inside sorts; a per-call memo brought it to 39 ms. **Cold instances:** when two page requests arrive at once a second function instance starts and loads the catalogue: 1.5-1.9 s for that page (seen in 4 of 8 first requests in the screenshot test). This is the same for `?feed=dynamic`; fix before switching the default (keep-warm or a smaller / lazily parsed snapshot).
**Simulation** (`scripts/spike/hybrid-sim.ts`: 5 personas + guest per gender, reactions through the real signal / codec path, measured on 120 outfits with the taste frozen; on-style = the pieces' dominant styles are the persona's styles): on-style share neutral -> after 20 / 50 / 100 signals: men smart bottoms + relaxed tops 48 -> 55 / 58 / 61%, streetwear / techwear 22 -> 39 / 48 / 41%, old money 43 -> 57 / 58 / 58%, minimal / scandi 19 -> 41 / 48 / 42%, sporty / gorpcore 19 -> 39 / 46 / 45%; women 40 -> 50 / 59 / 60%, 18 -> 38 / 38 / 38%, 20 -> 29 / 33 / 38%, 43 -> 69 / 68 / 71%, 20 -> 41 / 48 / 48%. Inside the "match" bucket 45-96% are on-style (most 60-80%). Variety stays: 8-16 dominant styles and 117-120 different tops per 120 outfits, the top style 20-52%, product repeats 3-24 per 120 outfits, score p10 0.84-0.85 (unchanged). Tests: a device that only likes classic still sees 10-13 styles and about 30% outside its style; 40 unlikes + 40 swap-aways of streetwear tops drop the taste match of streetwear tops from 0.62 to 0.09-0.11 and the on-style share from 38-40% to 27-28%; a cleared taste composes exactly like a new device. **Honest:** it does not over-fit (exploration and the near band keep about 40% of the feed outside the taste); it stays too random where supply is thin (women's streetwear bottoms, women's old money: the taste learns quiet luxury / minimalism instead), and "smart bottoms + relaxed tops" for men mostly yields knits with trousers rather than hoodies with trousers (few relaxed tops pass the score with tailored bottoms). Contact sheets: `scratchpad/spike/sheets/hybrid_smart.png`, `hybrid_sporty.png`.
**Cost per day** (composer path, Vercel list prices as in the cost section above; hybrid adds about $1.4 per million pages for the taste transfer): 1,000 daily users about $0.28, 100,000 about $28, 1,000,000 about $280 (with KV instead of client-held: +$80). **Settings (`app_settings`).** Table `key text pk, value jsonb, updated_at, updated_by`; RLS on, no policy, no grants for anon / authenticated. Seed: `feed_default = "base"` (allowed `base | dynamic | hybrid`), `sale_marker_enabled = true`. Changed only through the owner's Supabase connection (`update app_settings set value = '"hybrid"' where key = 'feed_default'`). The app reads them on the server only, through the gateway function `settings_get()` (service role behind the `pipeline` edge function; the web token has the right to call it; there is no Supabase secret key in Vercel and none is needed). `src/lib/settings.ts` validates every value against an allowlist (anything unknown or malformed falls back to the code default of that key), caches the result in memory for 45 s (15 s after a failed read, the last good value is kept) and the underlying fetch uses the Next data cache (`revalidate: 45`). The home page stays a static page (ISR, `revalidate = 60`, `x-vercel-cache: HIT`): the settings are read when it is regenerated and passed to `Feed` as `defaults`, so a change reaches visitors after about 1-2.5 minutes and no feed request makes a database call for it. `?feed=...` and `?sale=on|off` still win over the settings. `feed_default = hybrid` is now the real switch for the hybrid default (it replaces the planned `HYBRID_DEFAULT` environment variable); it is **not** switched. If the read fails, the code defaults apply (`base`, sale marker on), which equal the seed values, so behaviour is exactly as before.

**Job queue (`job_requests`).** Columns: id, job (CHECK allowlist: only `refresh_stock`; never add a job that makes paid AI calls), status `requested | running | done | failed`, requested_at / requested_by, started_at, finished_at, result jsonb (short summary), error, plus the runner state: progress jsonb, lease_until, heartbeat_at, attempts. Never two running at once: a unique partial index on `status = 'running'` plus a live-lease check in `job_claim()`. A running job whose lease ran out is taken over and resumed from its saved progress (idempotent: `offers_refresh` only changes differing rows); after 40 claims a job is marked failed. Request a job by hand: `select job_request('refresh_stock', 'me')`.

**Runner choice.** Three options were looked at. (1) *Vercel cron:* Hobby allows one call per day and a function may run at most 300 s; the full refresh takes about 5 minutes plus 1 minute for the snapshot, so a single call cannot finish it, and the secret would have to be set as an environment variable. (2) *GitHub Actions:* long enough, but it needs a long-lived database credential stored in GitHub, which breaks the rule that tokens expire. (3) **pg_cron + pg_net (chosen):** a cron job inside Supabase (a) enqueues one `refresh_stock` job per day at 01:15 UTC (02:15 / 03:15 in Europe, low traffic; skipped if a job was requested in the last 20 hours) and (b) every 5 minutes calls `runner_tick()`, which does nothing unless a job is open (requested, or running with an expired lease) and then POSTs to `/api/jobs/run` with the runner secret. The route (`src/app/api/jobs/run/route.ts`) answers `202` at once and works in the background (`after()`, max 300 s): it asks the database for a runner token (`runner_mint_token(secret)`: the secret is compared inside the database, a wrong or missing secret gives `401` and nothing runs), claims the job, works for up to about 200 s and saves its progress; the next tick continues until the job is done. No secret is created by hand: the runner secret is generated inside the database (Supabase Vault, `runner_secret`), never printed, never in the repo, chat or browser. The minted token lives 1 hour, has only the functions a refresh needs (`source_upsert, offers_refresh, shop_log_add, job_claim, job_progress, job_finish, outfit_inputs, composer_inputs, acc_inputs, snapshot_put`), exists in memory only (`useToken()`, never `process.env`, because the web app shares the process) and only its hash is stored. Nothing public can cost money: no AI call exists in the runner, and a call without the secret is rejected before any work.

**Daily refresh job.** `src/lib/jobs/refresh-stock.ts` uses the same per-shop logic as the script (`src/ingest/refresh.ts`; `scripts/refresh-stock.ts` stays for manual runs). Phases: *main* (all Shopify shops, concurrency 2, robots.txt and the per-host delay respected) -> *retry* (shops that answered 429: once, slowly, at least 10 minutes after the first pass, 6 s between requests to that host and 20 s between shops; if they answer 429 again it is logged and they wait for the next day) -> *snapshot* (rebuild the composer catalogue only if something changed; `src/outfits/build-snapshot.ts`, shared with `scripts/build-catalogue.ts`). Hosts answering 401 / 403 / 404 / 410 / 429 / 503 or disallowing the path are skipped; no proxies, no other route. `job_requests.result` keeps the summary (shops read / skipped, offers checked, sold out, back in stock, price changes, sales, delisted, 429 retried and recovered, snapshot).

**Shop log (`shop_refresh_log`).** One row per shop and attempt: shop, run_at, job_id, attempt (1, or 2 for the slow retry), status `ok | skipped | error`, http_code, products_seen, skipped_reason. Written on every run, including 401 / 403 / 404 / 410 / 429 / 503 skips. About 110 rows a day; indexes on (shop, run_at) and run_at; archive / partition by month later (nothing is deleted).

**Dashboard views** (all `security_invoker`, no grants for anon / authenticated, read-only): `dash_settings` (current settings), `dash_job_requests` (last 20 jobs with duration and result), `dash_shop_refresh_status` (latest result per shop and the number of consecutive failed runs, a run = the last attempt of a job), `dash_likes_by_style` (likes / unlikes per day, gender and top style of the liked product, last 14 days of the event log: index scans on `(event_type, created_at)` per monthly partition, no scan of old data). `dash_stock_freshness` is unchanged (it already shows last_seen per shop). **Not built: run id and effective cap per paid row.** Cost rows (`cost_usd`) live in four tables without a run id; adding it means changing four tables, every apply function and the budget guard (`src/lib/budget.ts` cannot await at process exit), which is not cheap and touches the money guard, so `dash_ai_spend` still compares a day with the default cap (10 USD). **Prices differ by visitor country (found on the first runner run, fixed the same day).** The first scheduled-style run changed 6,989 prices out of 15,635 offers (44%; the earlier manual run from the US had changed 182 of 13,082). Cause: many Shopify stores price by the visitor's country (Shopify Markets). Offers were ingested (and refreshed manually) from a US address; the runner runs in Dublin (`dub1`, the project region) and saw other prices (ratio to the ingested price 0.7-1.4 for dozens of shops), which it wrote over the stored ones. **What was done:** (1) `offers_refresh` has a guard (`p_guard`, default on): if more than 30% of a shop's matched offers would change price, nothing is applied and the shop is logged as skipped ("price shift N/M: other market?"); (2) the refresh asks every shop for the US market (`&country=US`, a standard storefront parameter, not a workaround for a block): for 95 of 107 shops this reproduces the ingestion prices (ratio 1.000, 95-96% of offers within 2%, the rest are real changes); (3) a repair run with the guard off put back the prices; for the 12 shops where the US market still differs from what the ingestion saw (aeyde, armedangels, colorfulstandard, drakes, houdinisportswear, missoma, nordgreen, rains, soulland, studionicholson, universalworks, whitemountaineering) the prices were restored from the original ingestion data in `raw_items` (cheapest available variant, same rule as the adapter); those shops are now skipped by the guard on every run (their stock and prices stay as ingested until they are ingested again or given a market of their own; they show up in `dash_shop_refresh_status`). Verification run afterwards: 95 shops applied, 0 price changes, 12 skipped by the guard, snapshot rebuilt. The old 3-argument `offers_refresh` still exists (dropping it hangs on this database); nothing calls it. **Open point:** the `currency` stored with some offers may not match the market they were ingested in (nanushka is labelled GBP but ingested US-market numbers); check before showing currencies to users.

## Per-shop market, currency label audit, 429 test (2026-10-22, evening)

**Per-shop market.** Table `shop_market` (shop, country, currency, frozen, reason, evidence): no row = the default market US (`REFRESH_COUNTRY`); a row with a country = send that `?country=`; `frozen` = the refresh does not fetch the shop and logs "frozen: reason" every run. ## Search tab (search by the searched piece)
- Search matches PIECES, not whole outfits. `rowsOf` (`src/lib/search-index.ts`) builds one row per top / bottom / shoe / accessory of each gender's in-memory catalogue (clean cutout card required; one-piece garments are never a top or bottom): family = family of the piece's dominant style, season = the piece's season mask (no mask = all seasons), extras = outfit-tag thresholds applied to the single piece (rain, evening, office, holiday, bold, colourful, formal). Tonal and pattern break are outfit-only and not offered. Index cached per catalogue object (a refreshed snapshot rebuilds it); no database read, `search_index` rpc is no longer used (left in place).
- Each result is composed around the matched piece by `composeAround` (`src/outfits/compose-around.ts`): the normal composer's rules (scoreOutfit hard rules + min score 0.84, relaxed to 0.80 on later attempts; pair score; shoe-length rule; accessory rules incl. women's slot limits; layout check), deterministic per piece, rest of the outfit from ANY style. Accessory search: base outfit that passes the accessory's hard rules, searched accessory first (`acc1`, the only one in colour), companions from the normal rules with the slot limits counted for it. Shoes search may give a one-piece garment + shoes (women).
- Order: own gender first, then the other gender (marked `og`, label + dimmed), total cap 30, one result per piece (a unisex piece once). Ranking: 0.6 family purity + 0.25 season specificity + 0.15 extra match, exact first, at most 5 per shop first within a tier. Fewer than 8 exact matches (both genders together): drop the extra, then the season. Candidates that cannot be composed are skipped (up to 2x30 candidates per gender are tried).
- Option counts (`/api/search?gender=`) count matched pieces of both genders; keys `item|family|season|extra`; options depend on the earlier steps only (part, family, season, extra). Empty combinations (5 families x 5 seasons x 8 extras x 4 parts = 800): 196 (was 564 men / 386 women of 1000 with outfit-level matching).
- Likes of the other gender's outfits are stored as a normal like without outfit context and without a taste signal (`og`).
- Rollback / switch: `app_settings.search_enabled = false` or `?search=0`. Women's accessories follow the catalogue (w2 set rules).
- Events table check constraint now allows `search_started` / `search_submitted` (added NOT VALID, no rows touched).
