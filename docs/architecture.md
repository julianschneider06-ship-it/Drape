# Architecture (data pipeline, roadmap step 2 part 1)

## Data flow

```
shop (Shopify /products.json, later feeds)
  -> SourceAdapter.fetchPage()      src/ingest/adapters/*   (polite HTTP, backoff, cursor)
  -> adapter.normalize()            common schema: src/ingest/types.ts
  -> scripts/ingest.ts              batch job, 100 items per call, resumable
  -> edge function `pipeline`       database gateway (service key never leaves Supabase)
  -> SQL function ingest_batch()    one set-based upsert per batch
  -> tables: raw_items, products, offers, product_images
```

AI classification is not part of this step. `classification_queue` exists and is empty.

## Scale decisions

- **Sources are config.** A Shopify store is one line in `src/ingest/sources.ts`. New kinds (feeds, Zalando) implement the same `SourceAdapter` interface; nothing downstream changes. Zalando is an inactive stub: the site blocks bots (Akamai 403), so the plan is a partner/affiliate feed.
- **Raw first.** Every source item is stored untouched in `raw_items` (jsonb + content hash). Re-normalizing needs no re-crawl.
- **Idempotent by construction.** Unique keys: `raw_items(source_id, external_id)`, `offers(source_id, external_id)`, `products(canonical_key)`, `product_images(product_id, url)`. Running a batch twice changes nothing. `ingest_batch` is one set-based SQL call per 100 items, not row by row.
- **Canonical products, many offers.** `canonical_key = sha1(brand | name | colour | gender)` merges the same product from several shops into one `products` row with several `offers`. When the colour is unknown we do NOT merge (the key uses source + external id), because a wrong merge is worse than a missed one. Found the hard way: Outdoor Voices sells one colour per product and has no colour field.
- **Compact keys, targeted indexes.** `bigint identity` ids (no random-uuid index bloat). Indexes only on lookup paths: offers by product and by (source, last_seen), images by (product, position), products by (category, gender, id) and by brand, partial indexes for un-normalized raw rows and for pending queue rows. Cursor pagination (`id > after`), never offset.
- **Resumable batch.** `ingestion_runs.cursor` is saved after every page. A killed or failed run continues from its cursor on the next start; `--fresh` starts over. The quota is spread across a store's feeds (e.g. women/men collections).
- **Polite crawling.** Only `/products.json` and `/collections/<handle>/products.json` (plus `/meta.json` once, for the currency). 1.5 s minimum gap per host, retries with 2/4/8/16 s backoff, honours `Retry-After`, identifying User-Agent. Never `/api/*`.
- **Background work, not in the request path.** Ingestion is a CLI batch (`npm run ingest -- --max 190`). The web page only reads.
- **No secrets in repo or browser.** Tables have RLS on and no policies. The service key stays inside Supabase; batch scripts and the Next.js server talk to the edge function `pipeline` with a token whose SHA-256 hash lives in `pipeline_tokens`. The Vercel token is a sensitive env var (`DRAPE_PIPELINE_TOKEN`). The AI key is not used by the web app.
- **pgvector enabled** (`extensions` schema), no vector columns yet. `gemini-embedding-2` returns 3072 dims by default; HNSW indexes allow up to 2000 dims for `vector` (4000 for `halfvec`), so the classification step should use `outputDimensionality` 1536 or a `halfvec(3072)` column.
- **Models are swappable.** `src/config/models.ts`: `DRAPE_MODEL_CLASSIFIER` (default `gemini-3.5-flash-lite`) and `DRAPE_MODEL_EMBEDDING` (default `gemini-embedding-2`). The REST API accepts the `AQ.` key through the `x-goog-api-key` header.

## Known limits / next scale steps

- Prices are in each store's currency (from `/meta.json`), not converted. Stale offers are trackable via `offers.last_seen_at`, but nothing marks them as gone yet.
- Colour is missing for about 24% of products; the classification step will derive it from the images.
- `/sample` orders by id, so it is grouped by shop. The real feed will use precomputed candidate pools.
- 400 hidden orphan product rows (status `hidden`) remain from the first sample run; delete them when convenient.
- At millions of rows: partition `raw_items` by source or archive old payloads; run `ingest_batch` calls from a queue or cron (Edge Function / Vercel cron).

## Classification (taxonomy v1, tested on one product)

- Taxonomy and strict JSON schema: `src/classify/taxonomy.ts` (`TAXONOMY_VERSION = "v1"`). 10 style weights (0..1, never a single label), category, gender, colors, pattern, material, silhouette, fit, boldness, formality, outfit_role, season, confidence. Output is forced by `responseJsonSchema` and validated again with Ajv.
- Results: `product_classifications` (unique per product + taxonomy version + model, so nothing is classified twice) and `product_embeddings` (`vector(1536)`, L2-normalized, from the product image). Model name and version, token usage, cost and latency are stored with each row.
- One-product test: `npx tsx scripts/classify-one.ts <product_id>`. About $0.0011 and 3.4 s per product (classification + image embedding).

## Image pre-selection and feed readiness (step 2, part 2)

- **Slots.** The feed shows 3 stacked slots: top, bottom, shoes. `feed_slot` is `top` (tops AND outerwear), `bottom`, `shoes`, `full_body` (dresses, jumpsuits, sets) or `none` (accessories). `is_outer_layer` marks jackets/coats worn over another top.
- **Free pre-selection first, AI second.** Every image gets free scores (`product_images`: `bg_whiteness`, `object_fill`, `view_hint`, `score`, `feed_rank`, `selected`): Shopify position, filename/alt hints (front/flat/packshot good; back/detail/model/lifestyle bad), aspect ratio, and a pixel check on a 200px CDN thumbnail (border plainness x brightness, how much of the frame the product fills). The best image is the feed candidate (rank 1), the runner-up is rank 2. `scripts/preselect-images.ts` is idempotent (`analyzed_at`), runs as a backfill over all products and as the step after ingestion for new ones (it only touches unanalysed images). Only ~6 images per product are analysed; all images come from the stored raw payloads, no re-crawl.
- **AI sees one image.** `scripts/classify.ts` reads the queue (`claim_classification_batch`, `for update skip locked`, stale locks re-claimed after 10 min, max 3 attempts) and sends only the pre-selected image plus title/brand to Flash-Lite. If `feed_suitability` < 0.5 (or the JSON is invalid) it retries once with the runner-up and keeps the better result. Idempotent via `product_classifications(product, taxonomy_version, model)` plus an `input_hash`; unchanged inputs are never sent again. A hard cost cap stops the run. Model name/version, tokens and cost are stored on every row. The job is a batch script; nothing in the web app can start it or spend money (the web token is read-only on the gateway).
- **feed_ready.** `feed_ready = !has_model AND !needs_cutout AND feed_suitability >= 0.7` (config `FEED_READY_MIN_SUITABILITY`). Otherwise `image_status = needs_image_work` with `image_reason` = `has_model | needs_cutout | low_suitability`. ALL products are classified (attributes are needed anyway), but only `feed_ready` products are eligible for the feed. Partial index `products_feed_ready_idx (feed_slot, gender, id) where feed_ready`.
- **Later: image work job (not built).** Products with `needs_image_work` get processed by a separate background job (background removal / cutout or regeneration), the result is stored in OUR OWN storage (rights, speed, stable URLs), the product gets a new `feed_image_url`, and `feed_ready` flips to true. Nothing else changes.
- **Embeddings** are made from the final chosen image (1536 dims, L2-normalized) with an HNSW cosine index (`product_embeddings_hnsw_idx`).
- **Cost levers at scale:** Gemini batch mode (50% off), a cheaper model, lower image resolution (`mediaResolution`), context caching for the long static prompt, and classifying each product once.

## Test results: 200 products (taxonomy v2, gemini-3.5-flash-lite), 2026-10-19

- 201 classified (incl. product #10), 0 failures, JSON invalid on the first try in 3 of 303 calls (~1%), always fixed by the single retry.
- Cost: $0.0028 per product incl. runner-up retries (about 50% of products retry), plus $0.00012 for the image embedding. Cheaper `gemini-3.1-flash-lite` (the 2.5 Flash-Lite is closed to new users): $0.0019 per product, same feed_slot/category on 50/50 products, 96% same feed_ready.
- First image rejected by Gemini (suitability < 0.5) for 50% of products; the runner-up was better in 34 of 102 retries. Stores that only photograph on models (Fashion Nova, Armedangels, Gymshark, Outdoor Voices) are 11-44% feed_ready; stores with packshots (Taylor Stitch, Aimé Leon Dore, Kith, Allbirds, Pangaia, Rains) are 73-100%.
- Embedding neighbours (5 seeds) look visually sensible: jackets near shirt jackets/bombers, shoes near shoes, dresses near dresses. They also pick up photo style (Pangaia's warm-grey backdrop).
- Ideas not yet tested: `mediaResolution` low (image tokens are ~half of the input), context caching of the static prompt, skipping the runner-up retry for model-only shops, Gemini batch mode (-50%).

## Packshot stores, cheaper classification, backdrop tone (step 2, part 3)

- **Store selection is data-driven.** A store is only added if `/products.json` works AND a cheap vision check (`scripts/probe-models.ts`, 3.1 Flash-Lite, low resolution, ~$0.0003 per image) finds a model-free image among the first 5 images of most sampled products. Plain background is NOT enough (Mother Denim, AGOLDE, Good American, Studio Nicholson are plain but on models). `scripts/probe-store.ts` shows the gender/category mix. Adding a store stays one config line (`src/ingest/sources.ts`, options `brand`, `defaultGender`, `exclude`, `max`).
- **Default classifier is `gemini-3.1-flash-lite`** (`DRAPE_MODEL_CLASSIFIER` to change) with `mediaResolution: low` (`DRAPE_MEDIA_RES`). Low resolution cut input from ~2,040 to ~1,290 tokens per call: same feed_slot / category / has_model / feed_ready on 50/50 products, pattern 98%, colour 96%, fit 94%, material 92% agreement.
- **Retry policy is derived from data, not hardcoded.** `store_retry_policy()` looks at past classifications per store: if the first pick is rejected (suitability < 0.5) for >= 80% of products and the runner-up helped in <= 30% of the retries (needs >= 12 products), the runner-up retry is skipped for that store. New stores learn this from their first products.
- **Already classified = skipped.** A product with any v2 classification is never sent again (unless `--force`); the input hash also covers prompt revision, model and image resolution.
- **Backdrop tone.** Plain light-neutral backdrops (e.g. Pangaia's warm grey) count as feed_ready. `product_images.bg_color` (median border colour) and `whiten_factor` (CSS `filter: brightness(x)` that turns the backdrop white; capped at 1.3) are stored, copied to `products.feed_bg_color / feed_whiten`. `mix-blend-mode: multiply` removes WHITE backdrops on a coloured page; for a grey backdrop on a white page use the brightness factor.
- **Brand clean-up without changing keys.** `brandKey`/`keyBrand`: the display brand can be renamed (Gymshark) while the canonical key keeps using the old string, so re-ingest never creates duplicates. Existing rows were updated with an idempotent `update ... where brand like 'Gymshark |%'`.
- **Scale levers for the classification job:** parallel workers are safe (`for update skip locked`); cost per product is ~$0.0011-0.0013; Gemini batch mode (-50%) is the next lever for the million-product run.
- **Operational note:** the Supabase MCP tool hangs on destructive SQL (DROP/DELETE/TRUNCATE); migrations are written without them.

About $0.0013 per product. 8,357 products in ~50 min with 2 parallel workers (~2.8 products/s); the data-derived retry policy skipped the runner-up retry for Fashion Nova, Armedangels and Gymshark (~470 saved calls).

## Outfit feed prototype (step 3)

**Flow.** `scripts/build-outfits.ts` (background job) -> table `outfit_pool` (precomputed cache; outfits are NOT a saved unit for users, only products are liked) -> `feed_list()` SQL function -> `/api/feed` (Next route handler, server-side token, rate limited) -> `Feed` (client). Nothing is computed per request.

**Pool (`outfit_pool`).** One row per (gender, top, bottom, shoes); `bottom_id = 0` means a full-body piece (dress, jumpsuit, set) in `top_id` with shoes below. Upserted by that unique key, `run_id` per run, rows not produced by the latest run are set `active = false` (no deletes, re-runnable). Each row has `score`, `style_key` and `feed_order` (the final feed sequence per gender). Only feed-ready, in-stock products with feed_slot top/bottom/shoes/full_body; underwear/swim/sleepwear/house slippers are excluded.
- **Candidate generation** avoids the n^3 blow-up: for every top and every bottom (bottoms are the scarce slot) keep the 10 best partners by a cheap pair score, then pick the 3 best shoes among all shoes with the full rules; full-body pieces get their 6 best shoes. ~65k candidates per gender, 40 s total.
- **Rules (`src/outfits/score.ts`)**: cosine of style_weights between pieces (34%), colour harmony = neutral base + at most ONE accent colour (22% + multiplicative penalty for 2+ accents), formality closeness (16%), season overlap (10%), silhouette balance (18%: no oversized x oversized unless streetwear-like), pattern clash penalty (2+ patterned pieces), at most one statement piece (statement_level >= 0.7), hard rejects: no shared season, warm-only piece (shorts, sandals) next to cold-only piece (coat, fleece, boots), more than one statement piece. Minimum score 0.84. Pieces are also excluded by name (boxers, pyjamas, swim, sleepwear) and a lone vest/gilet as the only top is penalized.
- **Selection** = by score with per-product caps (top 4, bottom 7, shoes 6, full-body 5 outfits). **Order** = weighted shuffle (score^6) followed by a greedy pass: no product repeated within 12 outfits, no same style 3 times in a row, no same store twice in a row.
- **Pages and variety**: the feed is split into fixed pages of 6 outfits (`feed_order` in [6k, 6k+6)); a device's first visit starts on page `hash(device_id) % pages`, afterwards the client sends the cursor (remembered per gender in localStorage). A page with a cursor is identical for every device, so `/api/feed?cursor=` is CDN-cached (`s-maxage=300`, ~0.15 s); only the start page is per device. Query = index range scan on `(gender, feed_order) where active`, ~16 ms for 6 outfits.

**Rendering.** `products.feed_bbox/feed_aspect` (job `scripts/bbox-feed-images.ts`, idempotent) hold the content bounding box of each feed image; the client crops to it with CSS container units so every product fills its slot equally. Backdrops are blended into white with `mix-blend-mode: multiply` plus `brightness(255 / lowest backdrop channel)` (pure multiply cannot whiten a grey backdrop). The next 3 outfits' images are prefetched; the CDN resizes via `?width=`.

**Event log (`events`, append-only, partitioned).** Partitioned by month on `created_at` (`events_pYYYYMM` plus a default partition); `ensure_event_partitions(n)` creates future partitions and must run monthly (cron) - 12 months are created. A trigger forbids UPDATE/DELETE. Types: impression, dwell_ms, like, unlike, tap_product, view_product_click, scroll_past; columns: device_id, product_id / product_ids, outfit_id, slot, feed_index, gender, dwell_ms, client_ts, created_at. Clients batch (20 events or 5 s, `sendBeacon` on hide); `events_append` takes max 100 per call. Indexes: (device_id, created_at), (product_id, created_at), (event_type, created_at) per partition.
- **Plan at scale**: step 4 reads events incrementally (watermark on id/created_at) to update compact per-device taste vectors; old partitions are detached and exported to cold storage (Parquet) after ~3 months while aggregates stay in Postgres; if volume grows, move ingestion to a queue (Edge Function / Kafka-like) and keep Postgres for aggregates. Likes live in `likes (device_id, product_id)` (soft toggle), history is in the log.

**Gateway rights are data.** `pipeline_tokens.allowed_fns` (per token) and `pipeline_rpc_allowlist` (callable functions): adding a function needs an insert, not a redeploy. The web token may only call feed/likes/events/review functions.

**Results (first prototype, 2026-10-20).** Pool: women 3,380 outfits (806 full-body, 2,478 distinct products), men 1,978 (46 full-body, 1,572 products). Dominant styles: women minimalism 27%, quiet_luxury 13%, resort 10%; men classic 40%, minimalism 16%, workwear 14%. Speed: database 16 ms per page; end to end uncached 0.55-0.95 s from outside the EU (several hops), CDN-cached pages 0.15-0.2 s; one 30 s stall was seen once, so the web path now has a 7 s timeout + one retry and the client retries once. Vercel functions run in `dub1` (next to the Supabase region eu-west-1, `vercel.json`).
**Known weak spots / next:** only three of the four slots can be full for men (men's full-body = 46); style mix is skewed (minimalism / classic); a few novelty pieces (ski-print trousers) slip through; some images still carry a faint non-uniform backdrop gradient (a real cutout job would fix it); the gateway adds ~0.5 s per database call from far away, so the long-term fix is a direct, narrowly scoped database role for the web app plus more CDN caching.

## Feed layout v2: outfit collage (visual only)
The outfit is no longer a straight column of three equal slots but a collage on one canvas. Nothing in the database, pool or scoring changed.
- **Files.** `src/lib/layout/config.ts` is the ONE place with numbers (sizes by garment class, margin zone, jitter, overlap ranges, all templates). `src/lib/layout/engine.ts` is a pure function `computeLayout(pieces, template, seed, canvas) -> rectangles` (no React). `src/components/OutfitCanvas.tsx` only draws the result with percentage positions.
- **Sizes.** Garment class comes from the product name (regex, no DB change): top, outer, longcoat, trousers, shorts, skirt, longskirt, shoes, full. Each class has a max width / max height as a fraction of the canvas (trousers ~48% of the height, shoes ~32% of the width, shorts/skirts lower height cap, dresses up to 65%). A piece is fitted into that box keeping its measured content aspect (`feed_bbox`).
- **Templates.** 6 three-piece templates (A-F) and 3 full-body templates (FA-FC), each also mirrored (suffix `m`): 18 in total. The template is picked by `hash(outfit id) % count`; the same hash seeds the small jitter (cluster +-2.5% x / 2% y, shoes +-1.5% x and +-3.5 degrees), so the same outfit always looks the same.
- **Overlaps.** Shoes are placed at the hem of the trousers/dress, overlapping it by 15-25% of the shoe height, z-order above. Top overlaps the waistband by 3-6% (top above bottom). Everything is scaled down if the cluster does not fit, centred and clamped to the canvas.
- **Margin zone.** 18% of the width on one side (the other side in mirrored templates) stays empty on purpose for the accessories column later; nothing is placed there.
- **Interaction.** Each piece is a tap target the size of its cropped box; the topmost piece (z-order) wins in overlaps. One small heart per product sits at the corner of its box with the least overlap. Canvas size follows a ResizeObserver on the scroller (max width 416 px, centred).
- **Debug.** `/?layout=A` (or `FB`, `Cm`, comma list: first match for the outfit kind wins) forces a template; `&debug=1` shows tap boxes, the template id and the margin zone.
- **Image width.** `feedSrc(card, class)` requests a width from the piece's max size and the share of the image its content covers, so prefetch and render use identical URLs.
- **Known limits.** `mix-blend-mode: multiply` lets a trouser colour shine through light shoes where they overlap; some shoe photos have a faint box backdrop that shows over the trousers (both are fixed by the later cutout job); a few "full body" items are really two-piece sets or shirt-dresses and look small.

## Cutouts: background removal of feed images (step "cutout")
Feed images carry the shop's backdrop (a faint box that showed where shoes overlap trousers). A background job now stores a transparent, cropped copy per feed-ready product; the feed uses it when it exists and falls back to the original photo (with the multiply blend) otherwise.
- **Model.** `isnet-general-use` (ISNet / DIS, Apache-2.0) through `rembg` + `onnxruntime` on CPU: free, runs on our side, no API. Chosen by test on 50 shoes + 20 tops/bottoms against `birefnet-general-lite` (MIT): same visible quality and the same guard results, but BiRefNet-lite needed ~12.8 s per image and ~9 GB RAM against ~2-3 s and ~1.8 GB for ISNet on the same CPU. If a shop already delivers a transparent PNG (Allbirds etc.), its own alpha channel is reused and no model runs.
- **Job.** `scripts/cutout/worker.py` (core: `cutout_core.py`, runner: `run_all.sh`). Order shoes, bottom, top, full_body. Work list = DB function `cutout_todo(slot, after, limit, model, version, shard, shards, retry_failed)`: feed-ready products without a result for this (model, version), or whose `feed_image_url` changed (`cutout_src`). So it is idempotent and resumable (kill and restart any time) and never re-processes unchanged products. Parallel: N processes with `--shard i --shards N` split the id space (id % N). Batches of 30: one RPC for the list, parallel downloads, inference, parallel uploads, one RPC `cutout_apply` for the results. A failing batch is retried after 15 s; a failing image is flagged, never blocks the batch. Not in the request path: the web app only reads finished columns.
- **Storage.** Public-read bucket `cutouts`, files `v<version>/<product id>.webp` (transparent WebP, cropped to the content bbox + 1.5% padding, max 900 px long side). The worker has no storage key: the `pipeline` gateway hands out signed upload URLs (`sign_upload`, only for that bucket and path pattern, only for tokens with that right). Supabase serves these with `cache-control: no-cache` (ETag revalidation); a long-cache domain/rewrite is a later optimisation.
- **Columns on `products`.** `cutout_url`, `cutout_status` (`ok` / `failed`, null = todo), `cutout_reason`, `cutout_model`, `cutout_version`, `cutout_quality` (0..1), `cutout_aspect`, `cutout_src`, `cutout_at`. `product_card()` returns `cutout` + `cutout_aspect` only when status is ok and `cutout_src` equals the current feed image.
- **Quality guard** (on the mask, per slot limits in `cutout_core.LIMITS`): foreground area ratio (too small / whole image), fragments (a pair of shoes = 2; specks and strings below 3% of the largest piece are dropped), border touching (product cropped by the photo frame), holes (enclosed regions that are NOT backdrop-coloured; real gaps between straps stay), undecided edge pixels, and recall of strongly non-backdrop pixels (catches cut-off laces, soles, sleeves, straps; shadows are ignored). Small holes are filled, the inside of the shape is forced opaque, the edge is eroded 1 px to avoid a halo. Failed products keep the original image and carry the reason.
- **Feed.** `viewCard()` swaps a product to its cutout (bbox = whole file, aspect = cutout aspect, no multiply) so the layout engine and the tap boxes use the cutout's real box; originals keep bbox + multiply. Debug: `?cut=off` shows the originals; with `?debug=1` a button toggles cutouts on/off live for the same outfit. Product sheet and /likes still show the original photo.
- **Scaling.** The job is CPU bound (~3.5 s per image per core). One 4-core box does about 1 image/s (~4,000/hour); the 6,700 feed-ready images of today take about 1.5-2 hours. For millions of products: the same worker as stateless containers (one per core or per GPU node), N shards by id, queue-style work list from the database (already how it works), new products only (each product once per model version), and a GPU (about 20-50x faster) or a smaller distilled model for the bulk. Storage is ~69 KB per cutout on average (436 MB for 6,519 files, so about 70 GB per million products); lowering MAX_SIDE or the WebP quality shrinks that.

**Results (2026-10-20, model isnet-general-use v1, cost $0):** 6,724 feed-ready shoes/bottoms/tops/full-body products processed: 6,519 ok (96.9%), 205 failed and kept on the original image. Shoes 1,660 ok / 64 failed (16 image 404, 18 photo cropped by the frame, 15 holes, 15 cut_off); bottoms 1,164 / 26; tops 3,233 / 100 (fragments 24, holes 25, uncertain edges 20, cut_off 19, too_small 7, 404 3, empty 1: mostly white tees on white backdrops and striped/checked shirts where the model leaves holes); full_body 462 / 15. Speed: ~3.7 s per image per process (1 CPU thread), 4 processes = ~1.1 images/s; the whole run took about 2 hours including two restarts. 394 feed-ready products with slot `none` (accessories) are not processed.

## Image check, next-best image, pool eligibility (multi-item images)
Some product photos show several items (three tees in a row, stacked garments). We do not try to cut out "the front one"; instead each product image gets a cheap AI check and a failed image is replaced by the next best photo of the same product.
- **Check (`scripts/image-check.ts`, rules in `src/imagecheck/schema.ts`).** Background job, batched (40), parallel (8 calls), resumable and idempotent: the work list is `image_check_todo(slot, after, limit, model)` = feed-ready products whose current feed image has been through the cutout job and has no row yet in `product_image_checks` for (product, image, model). The model sees the cutout (flattened on white) or the original if there is no cutout, at ~512 px with `MEDIA_RESOLUTION_LOW`, strict JSON: `item_count` (a pair of shoes = 1, a clearly-one-product set = 1), `is_single_product`, `defects[]` (hanger, mannequin, cropped, folded, text_overlay, model_visible, other), `confidence`. Default model `gemini-3.1-flash-lite` (`DRAPE_MODEL_IMAGE_CHECK`). Serious defects (config `SERIOUS_DEFECTS`): hanger, mannequin, cropped, text_overlay, model_visible; `folded`/`other` are only recorded. A check fails on `item_count != 1`, a serious defect, or confidence < 0.5. Every result is stored with model name + version, token usage and cost (`product_image_checks`), the verdict is denormalized on `products` (`image_check_status`, `image_check_src`, `is_single_product`, `item_count`, `image_defects`). Hard cost cap: `--cap` (default $6, summed over the whole table, stops the job).
- **Next best image.** `image_check_apply` marks a failed image (`product_images.check_status = 'fail'`; cutout failures mark it too) and switches `products.feed_image_url` to the best remaining candidate by pre-selection `score` (not `model`/`detail`/`back` views, score >= 0.3, never an image that already failed). The cutout job picks the new image up automatically (`cutout_src != feed_image_url`), then the check runs on it. A product with no candidate left gets `image_status = needs_image_work`, `image_check_status = failed` and `image_work_reason` (`multi_item`, `defect:...`, `cutout_failed`, `low_confidence`) and stays out of the pool. A passing check with a failed cutout also triggers the switch (a product without a usable cutout cannot enter the pool anyway).
- **Pool.** `outfit_inputs()` only returns products whose CURRENT feed image has `cutout_status = ok`, `image_check_status = ok` and `is_single_product` (all three tied to `feed_image_url` by their `*_src` columns, so a switched image is excluded until it is cut out and checked). Rebuild with `npm run outfits`.
- **New products.** `npm run ingest:all` (`scripts/pipeline.sh`) now runs ingest, pre-selection, classification, bounding boxes, then up to 3 rounds of cutout + image check (round 2/3 handle products switched to another image), then the outfit pool. Needs `DRAPE_PIPELINE_TOKEN`, `GEMINI_API_KEY`, and `PY` = a Python with rembg/onnxruntime.
- **Later:** merge `item_count` / `is_single_product` / `defects` into the classification call (next taxonomy version) so the check costs nothing extra; this job then only covers images that are replaced afterwards.
- **Cutout file names** are now `v<version>/<id>-<hash of source image>.webp` (older files keep `v1/<id>.webp`); the gateway accepts both.

## Feed layout v3: rule-based outfit layout (replaces the random templates for standard outfits)
- **Files / switches.** `src/lib/layout/rules.ts` (pure `computeRuleLayout`), all numbers in `src/lib/layout/config.ts` under `RULES` (+ `SIZE`, `PIECE_SCALE`, `MARGIN_ZONE`). `RULES.enabled = false` brings the old random templates back; `RULES.random = true` adds jitter/shoe tilt on top of the rules. The old 18 templates stay in the repo and are used when `?layout=A` (debug) forces one. `?debug=1` draws the left axis (blue, 38%), the canvas centre axis (green, 50%), the hem/waist lines (red, same width at the seam), the tap boxes, the free margin zone and the binding constraint in the label.
- **Stacked (default).** Top above bottom, gap `seamGap` (2.5% of the canvas height), both centred on the axis `axisX` (38% of the width, so the pair sits in the left half). Seam match: `w_top * hem_ratio = w_bottom * waist_ratio`; `w_top / w_bottom` is clamped to `ratioClamp` (0.75-1.35), equal bbox widths when a measurement is missing. Size: the largest bottom width k for which all class caps (`SIZE` x `PIECE_SCALE`) and the axis width hold; if the whole stack incl. shoes is taller than the canvas, everything is scaled by the same factor (keeps the match). Edge margin `edgePad` 2.5% of width and height. Shoes: centred on the canvas centre axis (50%), overlapping the trouser hem by `shoeOverlap` (20% of the shoe height, within 15-25%), z-order above the trousers.
- **Folded / not spread.** If the top or the bottom is not `spread_front` (or a top's mask is a compact rectangle, see below): top upper-left, bottom upper-right, exactly equal bbox height, as large as the half-width and the upper half allow; shoes at the centre axis in the lower half (`foldedShoesCy`).
- **full_body.** The item on the left axis (38%), shoes on the centre axis overlapping its hem.
- **Enlargement.** `PIECE_SCALE` 1.13 -> 1.243 (x1.10). Where the cap kicks in (540 real outfits, 390x844 phone): stacked outfits (433): bottom class cap 195, top class cap 238 (the top limits size when its hem is narrower than the waist), canvas height 174 (stack + shoes too tall, everything scaled down uniformly); full_body (80): class height cap 75, width cap 5; folded (27): half-width. The axis width and the edge margin never bound anything on a 390 px phone; nothing is clipped (0 pieces outside the canvas, 0 in the margin zone).
- **Data jobs (background, idempotent, once per product and image, resumable).**
  - `presentation` (`spread_front | folded | other`) is part of the image check (`ic2`, `src/imagecheck/schema.ts`, gemini-3.1-flash-lite, low resolution, strict JSON), so new products get it right after the cutout. Backfill for the products that already passed the old check: `npx tsx scripts/image-check.ts --presentation` (own cap `--cap`, default $3; table `product_presentation_checks`). Run: 4,640 products, $1.11; 4,553 spread_front, 70 folded, 17 other.
  - Measurements `scripts/cutout/measure.py` (`measure_core.py`): from the cutout alpha mask, as ratios of the cutout FILE width (content + 1.5% padding): `hem_ratio` (tops) = median width of the run containing the centre line over a band 1%-6% of the height above the lowest centre-line row of the body, so sleeves/cuffs that hang lower or are separated by a gap are ignored; `waist_ratio` (bottoms) = same at the top (2%-10% below the highest centre-line row); `shape_fill` = mask area / bbox area. Failure when the band is unstable (spread > 25%) or the ratio is outside 0.25-1.0. Results: bottoms 1,108 of 1,130 measured (98%); tops 2,745 of 3,194 (86%; 422 unstable, 27 out of range - mostly sleeves that merge with the body down to the hem); those fall back to equal widths. 24 spot-checks (tees, long-sleeve sweaters, jackets, jeans, trousers, shorts, skirts) were checked on a contact sheet with the measured lines; two earlier versions (band anchored at the bbox bottom, band too high) were wrong for long sleeves and were replaced.
  - Both go to the feed card (`product_card`: `presentation`, `hem`, `waist`, `fill`, only while they belong to the current image / cutout).
- **Presentation vs geometry (cross-check).** Tops with a compact rectangular mask (`shape_fill` >= 0.90): 54 are `folded` by the model, 19 are `spread_front`; the 12 we looked at were all folded button-down shirts the model called spread. So the layout treats a top with `fill >= foldedFillMin` (0.90) as folded too (`RULES.foldedFillMin`). Tops with fill < 0.85: 1 of 2,962 folded (agreement). Bottoms: the mask fill does not separate folded from spread (both 0.75-0.90); by aspect >= 0.8 there are 57 "geometry says folded, model says spread" cases, all of them looked like swim bottoms, shorts and wide trousers, i.e. correct as spread; so no geometry override for bottoms.
- **Outfits in the pool by layout:** men 1,683 stacked / 159 folded / 48 full_body; women 2,445 stacked / 44 folded / 791 full_body. Stacked pairs without both measurements (equal-width fallback): men 197, women 457.
- **Seam match on 374 measured stacked pairs (sample):** exact for 230 (61%); the clamp 0.75-1.35 binds for 144 (38%), because a top's hem is often much narrower than a trouser's waist (hem about 0.55 of the file width, waist about 0.8). With a clamp of 0.6-1.7 the match would be exact for 350 of 374 (94%). The clamp is the user's choice, so it stays at 0.75-1.35 (`RULES.ratioClamp`).

## Swap a piece (swipe sideways)
- **Alternatives (background job).** `scripts/build-alternatives.ts` fills `outfit_alternatives(outfit_id, slot_key, rank, product_id, score, scorer_version, active)` (slot keys top | bottom | shoes | acc1..3; `top` is the dress in full-body outfits) and `outfit_alt_state(outfit_id, input_hash)`. Up to 6 alternatives per slot, ranked with the outfit builder's own `scoreOutfit` (style, colour, formality, season, silhouette, pattern, one statement piece, hard season/weather rules), with the other pieces fixed. Hard rules: same gender, feed-ready with clean cutout and measurements, not in the outfit, same presentation class (folded stays folded), the outfit's accessories must still pass their rules, no two alternatives of the same brand in a row where possible. Accessories: same `accessory_type` first, other types only if fewer than 3 (exclusivity rules: one head item, one bag, one neck item, one statement piece, accent colour). Idempotent and resumable: an outfit is only recomputed when the hash of its pieces, accessories, the eligible candidate set and the scorer version changed (`--force` overrides). Result: 5,161 of 5,170 outfits covered, 24,734 slots, 5.99 alternatives per slot on average, 53 slots with fewer than 3 (37 tops, 16 bottoms).
- **Lookup.** Gateway function `alternatives_list(outfit, slot)` (also allowed for the web token `vercel-sample-page`), route `/api/alternatives` (CDN cache one hour). The browser fetches on the first swipe on a piece, loads the new piece's image BEFORE the swap and prefetches the next ones. State is in memory only (`src/lib/client/swap.ts`): swapped pieces stay while the user scrolls back and forth, reset on reload.
- **Gesture.** Pointer events on the outfit canvas with `touch-action: pan-y`: a drag counts as a swipe only if it starts on a piece (topmost piece under the finger, so shoes / overlays win), moves more than 14 px, mostly horizontally (|dx| > 2 x |dy|) and ends at least 44 px away; a vertical drag (|dy| > 12 and |dy| > 0.7 |dx|) cancels it, so scrolling is unchanged. Left = next alternative, right = previous (back to the original). End of the list: small bounce, nothing else. The tap that follows a drag is suppressed. The layout is recomputed by the normal engine (pieces animate to their new positions), the old piece slides out and the new one slides in.
- **Events.** New append-only event type `swap` (ctx: out = product that left, dir = next|prev, rank = alternative rank, 0 = original; product_id = product now shown; slot; feed_index). Hearts, taps, impressions and dwell use the piece currently shown. Not used for ranking yet.
